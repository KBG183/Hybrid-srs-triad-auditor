## 2. 運用障害および再発防止台帳 (Incident History)

### 2026-11-18 — INCIDENT-62 — インライン複数行PowerShell実行時の引用符ネスト展開不全・変数消失によるバックグラウンドタスク無応答ハング障害の再発防止

- **問題**: エージェントが `run_command` を介して `powershell -Command "..."` の複数行インラインスクリプトを実行した際、引用符の解釈異常により `$zipPath` や `$dest` などの変数名が消失し、`= '...'` のみ実行されて構文エラー（`The term '=' is not recognized`）が発生。プロセスが正常終了せずバックグラウンド非同期タスクとして無応答ハング（Hang）状態となり、ユーザーUIにエラーログが残留し続けた。
- **原因**: 外部CLI/ランタイムのコマンドラッパーにおいて、インライン文字列として渡されたPowerShellスクリプトの変数および二重引用符のパースが衝突・脱落したこと、および構文エラー発生時にプロセスが即座にクリーン破棄されず非同期ジョブとして放置されたこと。
- **恒久対策**:
  1. **インライン複数行PowerShell実行の全廃**: 単純な1行コマンド（`git status` 等）を除き、すべてのスクリプト実行は必ず事前に `scratch/` ディレクトリ配下へUTF-8物理ファイル（`.ps1`）として書き出した後、`powershell -ExecutionPolicy Bypass -File "絶対パス"` の単一コール形式のみで実行するよう最上位運用規約（`GEMINI.md` 第10条）へ明文化。
  2. **スクリプト内フェイルファスト（Fail-Fast）の強制**: 作成される全スクリプト冒頭に `$ErrorActionPreference = 'Stop'` を義務付け、軽微なエラーであっても即時非ゼロ終了（`exit 1`）させてバックグラウンドゾンビ化を遮断。
  3. **タスクライフサイクル監視**: 非同期タスク発生時は即座に状態を検知し、異常終了・不要タスクを `manage_task kill` により速やかに破棄して残存タスク数0件を維持。
- **状態**: `RESOLVED`

### 2026-11-17 — INCIDENT-61 — 多層交差検証品質判定（FAIL/REJECT）と台帳ステータス（PRODUCTION_PASS）間の不整合是正および全段Fail-Closed化

- **問題**: 4層統合監査（BATCH-08）においてQwen P0指摘（2件）、Codex要修正（FAIL）、Claude不承認（REJECT）が報告されていたにもかかわらず、台帳（CSV）に「パイプライン実行成功」に起因する `PRODUCTION_PASS` が誤って記録され、監査リポートとの間に判定矛盾が発生していた。また、Codex/Claude実行失敗時にコントローラーが警告のみを出力して正常終了（`exit 0`）するFail-Openの懸念が存在した。
- **原因**: 「監査パイプラインのプロセス実行正常性（Pipeline Execution Success）」と「監査対象仕様書の品質適合性（Specification Quality Verdict）」の定義混同、およびプロセス終了コード伝播処理の不足。
- **恒久対策**:
  1. `enterprise_audit_ledger.csv` における `BATCH-08` のステータスを `AUDIT_FINDINGS_REPORTED`（欠陥検知・改訂課題確定）へ即時是正。
  2. `hermes_controller.ps1` において、実行対象の各検証エンジン（Qwen, Codex, Claude）で実行時エラーまたは空出力が発生した場合、詳細リポートを出力した上で最終的に終了コード1（Fail-Closed）を返却するよう制御を厳格化。あわせて部分再試行時の重複トークン浪費を防止するため、対象ファイルのSHA-256ハッシュ照合に基づくスマート増分キャッシュ（`-UseCache`）をコントローラーに実装。
- **状態**: `RESOLVED`

### 2026-11-17 — INCIDENT-60 — PowerShell 5.1 Latin-1 HTTP デコードによるClaude監査リポート文字化けの検知およびRawContentStream直接読取への刷新

- **問題**: `audit/HERMES_Audit_...md` 内の Claude 5.5 監査セクションが `# ç›£æŸ»å ±å‘Šæ›¸...` のように文字化け（Mojibake）して記録され、法規監査結果が閲覧不能となった。
- **原因**: Windows PowerShell 5.1 の `Invoke-RestMethod` は、HTTP レスポンスの `Content-Type` に `charset=utf-8` が明示されていない場合（Anthropic APIは `application/json` を返却）、既定値として ISO-8859-1（Latin-1）を適用して文字列デコードを行うため、UTF-8マルチバイト文字が破損して格納された。

  3. 既存の破損リポートに対してLatin-1バイト再マッピングによるUTF-8復元スクリプトを実行し、正常な日本語法規監査文面を完全回復。

### 2026-11-17 — INCIDENT-57 — .NET ProcessStartInfoにおけるCP949バイト歪曲および空白パス引数分離によるCodex CLI失敗の解決

- **問題**: `call_codex.ps1` 実行時に引数分離エラー（`unexpected argument found`）および `Failed to read prompt from stdin: input is not valid UTF-8` が発生し、終了コード1で失敗。
- **原因**: 
  1. 空白を含む作業ディレクトリパス（空白区切りフォルダー名）が `ProcessStartInfo.Arguments` で適切に二重引用符エスケープされていなかった。
  2. .NET Framework 4.x の `Process.StandardInput` はOS既定のANSI（CP949）でエンコードされるため、日本語・韓国語プロンプトが破損してCLIへ伝達された。
- **恒久対策**:
  1. 空白を含む引数を自動判定して引用符で囲む `$escapedArgs` 処理を追加。
  2. `StandardInput.Write(string)` を廃止し、`[System.IO.File]::ReadAllBytes()` で取得したUTF-8生バイトを `$proc.StandardInput.BaseStream.Write()` で直接パイプストリーミングする無損失UTF-8パイプラインを確立。
  3. 単独実行で `gpt-5.6-terra` による 41.1秒、2,334文字の監査リポート生成（`SUCCESS`）および統合コントローラーでの正常完了を実証。
- **状態**: `RESOLVED`
