## FILE 1: `verify_repo_total_integrity.ps1` (Checks 6 & 9)

### Satisfied
- Same-directory temp file (`"${fullPath}.tmp.<guid>"`) gives atomic-rename semantics on the same volume.
- `finally` cleanup of the temp file.
- Check 9 is scoped to `md|java|json|ps1|csv`.
- `-Fix` is opt-in; the default path is detect-only.

### Defects

**1. [HIGH] Check 9 destroys legitimate non-UTF-8 content (corruption risk).**
It operates on raw bytes, not decoded text. In UTF-16 files (common for PowerShell-generated CSV/JSON on Windows PowerShell 5.1 via `Out-File`/`>`), every other byte is `0x00`. The scan flags the file, and `-Fix` strips every NUL, turning the file into mojibake-free garbage with no recovery. There is no encoding detection and no UTF-16 BOM check (`FF FE` / `FE FF`).

**2. [HIGH] Check 9 flags and "fixes" legitimate characters.**
- `0x0C` (form feed) and `0x1B` (ESC) can legitimately appear in `.md` (ANSI-colored log excerpts) and `.ps1`.
- `0x7F` (DEL) is not covered, so the detection range is inconsistent with the "control character" claim.
- Silent deletion of semantic bytes can alter signed or hashed content, test fixtures, or regex literals in `.java`/`.ps1`.

**3. [HIGH] Check 9 can bypass the BOM logic and corrupt multi-byte UTF-8.**
Stripping bytes `< 32` is safe for valid UTF-8 (continuation bytes are `>= 0x80`), but the check is unconditional on encoding. See defect 1 for the non-UTF-8 case. There is no validation that the output is still valid UTF-8 after the fix.

**4. [HIGH] Check 6/9 ordering and partial-write hazard.**
The BOM check and the control-char check are independent passes. If both run with `-Fix`, a file is rewritten twice (two replace cycles). A crash between them leaves intermediate state. Compute all fixes in memory and perform a single atomic write.

**5. [MEDIUM] `[System.IO.File]::Replace` pitfalls.**
- Passing `$null` as the backup is valid, but `Replace` fails if the destination is open/locked (antivirus, IDE, git). There is no retry and no explicit handling, and the surrounding code logs failure only through exception propagation.
- `File.Replace` does not preserve the original file's ACLs in all scenarios (it attempts to merge attributes/ACLs, behavior varies). Original file attributes (read-only) cause `UnauthorizedAccessException`.
- Cross-volume or network-share/subst/junction cases: the temp is in the same directory, so the same volume is guaranteed. OK. But on non-NTFS (exFAT, some network shares) `Replace` is unsupported and throws.
- Symlinks: if `$fullPath` is a symlink, `Replace` replaces the link target semantics inconsistently. This is not handled.

**6. [MEDIUM] Line-ending and "tracked files" assumptions.**
`$trackedFiles` provenance is not shown. If derived from `git ls-files`, paths with spaces or non-ASCII characters may be quoted/escaped (`core.quotePath`), causing `Test-Path` to skip them silently (`continue`). That is a **silent-skip, fail-open** behavior in a gate meant to be fail-closed. Skipped files are not counted or reported.

**7. [MEDIUM] Check 6 variable shadowing.**
Check 6 uses `$b` as a byte array; Check 9 uses `$b` as a scalar byte inside the loop (`$b = $bytes[$i]`). If both live in the same scope or the loop is later merged, this is a latent bug. Rename.

**8. [MEDIUM] Performance.**
`List[byte]` with per-byte `.Add` in PowerShell is very slow (interpreted loop) for large files. Use `[Array]::FindAll`/`Where` over a byte[] with preallocation, or a compiled `Add-Type` helper. The scan loop is also interpreted PowerShell. On a large repo this is a CI-time risk.

**9. [LOW] Counters.**
In `-Fix` mode `$bomHits`/`$ctrlHits` are not incremented, so the exit code is 0 after fixes. The working tree is now modified but the pipeline passes, so a "fixed" run can be green with uncommitted changes that are never staged. For a gate, a fix run should exit non-zero or require re-verification.

## FILE 2: `patch_ssot_literal.ps1`

### Satisfied
- `StringComparison.Ordinal` used for `IndexOf`.
- Single-match guard exists.
- Atomic same-directory replace with `finally` cleanup.
- UTF-8 **no BOM** on write.
- Empty-target and identical-string rejection (no-op rejected).

### Defects

**1. [HIGH] Single-match guard is incorrect for overlapping matches.**
The second search starts at `$firstIndex + 1`, so overlapping occurrences are detected (good). However, `-AllowMultiple` uses `String.Replace(string,string)`, which is **culture-sensitive in .NET Framework (Windows PowerShell 5.1)** for the 2-string overload, so it is not ordinal. Use `Replace(old, new, StringComparison.Ordinal)` (only available .NET Core 2.0+/PS 7) or implement a manual ordinal loop. This directly violates the "literal" guarantee and can match or skip ligatures and zero-width characters under culture rules.

**2. [HIGH] BOM handling on read is silently lossy and inconsistent.**
`ReadAllText(path, UTF8)` strips a leading BOM during decode. A file that had a BOM is rewritten without one: an **unlogged side effect**, which may be desirable but is not reported. Conversely, a non-UTF-8 file (e.g., Windows-1252 or UTF-16) is decoded as UTF-8 with replacement characters (U+FFFD). The patch then writes those back, **permanently corrupting** the SSOT. Use a strict decoder (`UTF8Encoding($false, $true)` with `throwOnInvalidBytes`) for both reads and the patch inputs.

**3. [HIGH] Line-ending normalization is not guarded.**
`ReadAllText` preserves CRLF/LF, but `-TargetText` passed on the command line, or from a file authored on a different platform, will often differ in line endings (CRLF vs LF) from the SSOT. Result: `TARGET_NOT_FOUND` (safe failure) or, worse, a replacement that introduces mixed line endings. There is no explicit policy (reject, normalize, or preserve).

**4. [MEDIUM] Control-character check scans the whole file, not the delta.**
Any pre-existing control byte in the SSOT makes **every** patch fail with a misleading "Replacement introduced byte" message. The check should compare against the pre-patch baseline, or scan only `ReplacementText`.

**5. [MEDIUM] Path traversal / scope escape.**
`$TargetFile`, `$TargetTextFile` and `$ReplacementTextFile` are joined to `$projectRoot` with no validation. `..\..\` or an absolute path (`Join-Path` with a rooted second arg in PS 5.1 does not discard the first, but UNC/`C:\` handling is inconsistent) lets the script read or overwrite files outside the repo. Resolve with `[IO.Path]::GetFullPath` and assert the result starts with `$projectRoot`. Also consider restricting `-TargetFile` to an allow-list, since the script name says "ssot".

**6. [MEDIUM] No integrity or audit trail.**
For an SSOT specification (the requirements baseline), there is no pre/post SHA-256 hash, no change log entry, no backup, and no dry-run (`-WhatIf` / `SupportsShouldProcess`). `[CmdletBinding()]` is declared but `SupportsShouldProcess` is not. Compliance (traceability, change control, e.g., ISO 26262/DO-178C/SOX-style requirements-traceability regimes) typically demands who/what/when and before/after hashes.

**7. [MEDIUM] Concurrency / TOCTOU.**
Read, then compute, then replace without locking. Two concurrent patchers produce lost updates. Add a mutex/lock file, or verify the file hash is unchanged immediately before `Replace`.

**8. [LOW] `$OutputEncoding`/`[Console]::OutputEncoding` set globally.**
These are process-wide mutations with no restore, which affects the caller if dot-sourced.

**9. [LOW] `-AllowMultiple` is unbounded.**
No expected-count assertion (`-ExpectedCount N`). A short target text can rewrite hundreds of locations. Success output should report the number of replacements; currently only a banner is printed and the replacement count is not emitted.

**10. [LOW] Success banner only.**
No exit-code contract is documented. It relies on `throw` + `$ErrorActionPreference='Stop'`, which yields exit code 1 under `-File` invocation, but a caller using `-Command` or dot-sourcing can behave differently.

## FILE 3: `run_quad_audit.ps1` (fail-closed propagation)

### Satisfied
- `$LASTEXITCODE` captured immediately after the native call, before any other command (correct).
- Non-zero exit short-circuits before the `.done` marker is created (good: the marker is only written on success).

### Defects

**1. [HIGH] Fail-open on a null/unset `$LASTEXITCODE`.**
`$linterExit -ne 0` evaluates to **false** if `$LASTEXITCODE` is `$null` (e.g., the process failed to launch, the `powershell` binary is not on PATH and raises a non-terminating error, or a prior state exists). `$null -ne 0` is actually `$true` in PowerShell, so that case is safe, but a stale `$LASTEXITCODE` from an **earlier** native command is possible if `& powershell` throws a terminating error that is swallowed. Reset `$global:LASTEXITCODE = $null` before the call and explicitly handle the `$null` case with a hard fail.

**2. [HIGH] `-ExecutionPolicy Bypass` weakens the supply-chain posture.**
It is applied to a script that is itself an integrity gate. Combined with no signature/hash verification of `verify_repo_total_integrity.ps1` before execution, a tampered linter would be run with policy disabled. Verify the linter's hash against a pinned value, or use `AllSigned`.

**3. [MEDIUM] Hard-coded `powershell` (Windows PowerShell 5.1) vs `pwsh`.**
Ambiguous host resolution via PATH (PATH hijacking). Use an absolute path (`$PSHOME`/`$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe`). Also add `-NoProfile -NonInteractive` so a user profile cannot alter behavior or hang CI.

**4. [MEDIUM] Only Stage 4 shown; the "native execution" claim is not verifiable.**
The instruction cites "fail-closed exit propagation on Stage 4 **and native execution**." Stages 1-3 are not provided, so I cannot confirm they use the same pattern. A missing stage check is a classic fail-open hole. Please supply the full file.

**5. [MEDIUM] `.done` marker has no content or integrity.**
An empty file proves nothing about what was verified (no commit SHA, timestamp, or stage results). A stale `.done` from a previous run is not cleared at start, so a later failure could still see the old marker. Delete it at pipeline start and write the commit SHA plus the hash of the verified tree.

**6. [LOW] `exit $linterExit`** propagates the code correctly, but exit codes above 255 are truncated on POSIX hosts, and 0-modulo-256 codes would read as success. Clamp or remap to 1.

## Cross-Cutting Compliance and Logic Risks

1. **Fix-mode vs gate-mode conflation.** The same script both mutates and verifies. A pipeline that runs `-Fix` and then commits defeats the purpose of an integrity gate. Mutation must be a separate, human-invoked tool, and CI must run verify-only.
2. **Inconsistent control-character policy.** Check 9 (strip `<32` except TAB/LF/CR) is mirrored in File 2, but File 2 **rejects** while File 1 **deletes**. Document one authoritative policy (and the same allow-list for FF/ESC/DEL).
3. **No unified encoding contract.** UTF-8 no-BOM is enforced for output, but nothing validates UTF-8 validity on input across the three scripts.
4. **No tests are cited** for the atomic-replace failure paths (locked file, read-only attribute, missing destination: `File.Replace` throws if the destination does not exist, which matters for first-time creation).
5. **Legal/compliance:** altering SSOT requirements without an audit trail may violate change-control obligations (traceability, tamper evidence) in regulated contexts. Silent deletion of bytes in tracked sources (File 1, Check 9) can also alter licensed or signed third-party content (license headers, vendored files) and invalidate checksums or signatures.
