## 1. 🔴 P0 Findings（Critical）

### [F-P0-01] 月60時間超の重畳割増マトリクスの内部矛盾と欠落（REQ-LABOR-001/003）

**事象**:
- REQ-LABOR-003 は「休日労働は60h算定から除外」としつつ、`overtimeMinutesOver60` の累積境界が**月次**でありながら、REQ-LABOR-001 は**日次・週次**でのみ時間外を算出している。両者の接続（月累計60h判定のためのセグメント分割順序）が未定義。
- 「時間外×深夜重複（60h以下: 25%+25%=+50%、60h超: 50%+25%=+75%）」は記載があるが、**時間外×休日×深夜の三重重畳**および**休日労働中の深夜（+35%+25%=+60%）と時間外の排他関係**の網羅テーブルがない。
- 月60h超部分の代替休暇（法第37条第3項）制度を採用する場合の割増率扱い（25%分を休暇付与に代替可）が仕様範囲外か対象内か不明。

**リスク**: 月60h境界を跨ぐ勤務、または月跨ぎ勤務で1円単位の誤差・割増誤適用が発生。

**要求修正**:
1. 完全な排他セグメント・マトリクス表（全8象限）を付録として規定すること。
2. 月60h累計判定は**暦月ではなく就業規則の賃金計算期間**（`payCutoffDay` 準拠）で起算する旨を明記すること（※法解釈上、1か月の起算日は就業規則で定める。暦月固定は `payCutoffDay` と矛盾する）。
3. 代替休暇制度を「対象外」と明示的に宣言すること。

### [F-P0-02] 法定休日の定義・特定ロジックの不備（REQ-LABOR-001/003）

**事象**: 入力 `isStatutoryHoliday` を BOOLEAN として受け取るが、
- **誰が・いつ・どう決定するか**が未定義（就業規則による特定、4週4日変形休日制、振替休日・代休との区別）。
- 「週1日または4週4日」を許容する一方、**4週4日の起算日**の保持場所がデータモデルにない。
- 日曜が法定休日・土曜が所定休日（法定外休日）の場合、土曜労働は**時間外（週40h超過時）**であって休日割増35%ではない。この区別規則が無い。
- 休日振替（事前振替）と代休（事後付与）で割増扱いが異なる点（振替なら通常日、代休なら休日割増発生）が未定義。
- 暦日0:00分割後の「休日区間」の**日次8時間枠・週40h枠からの除外**は規定されているが、通常日側区間の**週累計への算入規則**（分割後の前半のみ算入）が `priorWeeklyMinutes` の定義と整合しているか検証手段なし。

**要求修正**: `holiday_calendar` エンティティ（店舗別・期間別・法定/所定区分・振替履歴）を新設し、`isStatutoryHoliday` は入力ではなくサーバー側導出値とすること。

### [F-P0-03] 日次・週次残業の二重計上防止式の数理的欠陥（REQ-LABOR-001 処理3-5）

**事象**: 提示式
- `dailyOvertimeMinutes = max(0, prior+cur-480) - max(0, prior-480)`
- `weeklyAddition = min(cur, max(0, 480-prior))`

には以下の欠陥がある。
1. **所定労働時間が8h未満**の契約（例: 所定7h）での「所定超・法定内」は割増不要という整理は正しいが、`weeklyAddition` は日8h以内部分のみ週に算入する設計であるため整合する。一方で、**週40h超過の判定に日次残業分を含めない**（二重計上回避）という通達上の取扱いの出典が仕様内に明示されず、「週の法定労働時間の特例（常時10人未満の商業・接客娯楽業は週44h）」への分岐が欠落している。
2. **特例措置対象事業場（週44h）**: 飲食・小売（本システムの対象ドメイン）は常時10人未満であれば週44h特例の対象となり得る。**週40h固定は法令誤認の可能性**。
3. `priorWeeklyMinutes` が「法定休日および日次残業算定済分を除く」と定義されているが、日次残業分は通常「週40hの算定から控除」するのではなく、「日8h以内の部分のみで週累計をカウント」する（式は整合するが、`priorWeeklyMinutes` 入力の生成責任が呼び出し側かエンジン側か不明）。
4. **週の起算日**（就業規則上の曜日）が未定義。週境界の定義がないため週次判定が非決定的。

**要求修正**: 事業場マスタに `weekStartDay`、`weeklyStatutoryMinutes`（2400 or 2640）、`isSpecialProvisionEligible` を追加。変形労働時間制（1か月・1年単位）の対応可否も明記（非対応なら明示的に非対応宣言）。

### [F-P0-04] 不変スナップショットの永続性が不完全（REQ-LABOR-004、REQ-STAFF-002）

**事象**: 監査要求「immutable snapshot permanence」に対し、現行仕様は以下が欠落。
1. `payroll_settlement_line` に保存すべき**スナップショット項目の列挙がない**（時給、適用契約履歴ID、適用最低賃金値、休憩控除内訳、打刻原データのハッシュ、計算エンジンバージョン、丸め前分子/分母）。
2. 確定後の**不変性を物理的に担保するDB機構**（UPDATE/DELETE禁止トリガー、`REVOKE`、append-onlyテーブル、行ハッシュチェーン）が未規定。アプリ層のステータス検証のみでは直接SQLやバッチ・マイグレーションで改変可能。
3. **確定後の訂正手続**（打刻誤り・時給誤設定の事後発覚）が定義されていない。遡及訂正は**赤伝/黒伝（逆仕訳）による調整明細**として新規レコードで表現すべきだが、仕様が存在しない。→ 現状は「訂正不能」または「違法な直接改変」の二択になる。
4. 賃金台帳の**保存義務（労基法第109条・第108条、記録の保存は5年・当分の間3年）**に対応する保存期間・削除禁止ポリシー・退職者データの扱いが未記載。
5. 契約履歴 `store_staff_contract_history` は更新（`effective_to`）を許容しており、**確定済み精算が参照する履歴行の事後変更を防ぐ制約**が無い。`effective_to` の更新は未確定月に限定する旨が必要。
6. 退職処理で最終契約の `effective_to` を退職日で確定する際、**確定済み月の契約行を変更する経路**になり得る。

**要求修正**: `payroll_settlement_line` を完全 append-only 化（DBトリガーで UPDATE/DELETE を `SIGNAL SQLSTATE '45000'` 拒否）。スナップショット項目の必須列挙、`engine_version`、`input_hash`（SHA-256）の導入。調整は `adjustment_of_settlement_line_id` 参照の逆仕訳レコードで実装。保存期間は最低5年（法定3年＋安全マージン）を規定。

### [F-P0-05] 労基法第34条休憩の不完全実装（REQ-SHIFT-002 / REQ-LABOR-001〜003）

**事象**:
1. **閾値の誤用**: 法定は「労働時間が6時間を**超える**場合45分、8時間を**超える**場合60分」。仕様の自動算定は拘束時間 `<=360 → 0`, `<=525 → 45`, `>525 → 60`。拘束時間525分（8h45m）−45分休憩＝実労働480分（ちょうど8h）で整合するが、**拘束時間361〜405分（6h01〜6h45）に45分を付与すると実労働が6時間未満（316〜360分）になり過剰付与**。賃金カットを伴う場合（無給休憩）、過剰休憩付与は労働者の不利益になる。「拘束360分超→実労働が6hを超えるか」の判定は**実労働ベース**で行う必要がある。
2. **手動指定時の検証ロジックの穴**: 「実労働 > 8h で休憩 < 60」「実労働 > 6h で休憩 < 45」と記述されているが、**実労働は休憩に依存する循環定義**（実労働＝拘束−休憩）。「休憩を増やすと実労働が減り閾値以下になる」ため、判定は**拘束時間ベースの不等式**（拘束 > 360+45 かつ休憩<45 等）に書き換えるべき。
3. **一斉付与・途中付与・自由利用の原則（第34条第2項・第3項）**: 休憩は労働時間の**途中**に与える必要がある。始業直後・終業直前の休憩配置は無効。`breakIntervals` の**配置位置の検証がない**。
4. **休憩の分割**（15分×3回等）は可能だが、最小単位の規定がない。1分単位休憩の水増し運用を許す。
5. **打刻後の休憩（実績）と計画休憩（`planned_break_minutes`）の乖離**: 給与計算は `breakIntervals`（実績）を使うが、法定休憩の**実績ベース適合チェックが給与側にない**。休憩未取得（付与義務違反）の検知・アラートがない。
6. **休憩中の呼出待機（手待ち時間）は労働時間**である点の扱いが未定義。
7. **勤務間インターバル**・連続勤務日数・週1休日確保（第35条）の検証がシフト確定時に無い。
8. 年少者（18歳未満）は深夜労働原則禁止（第61条）、時間外・休日労働制限（第60条）、変形労働時間制の適用制限。**飲食・小売アルバイトでは高校生雇用が頻出**であるにもかかわらず、`birth_date` がデータモデルにない。

**要求修正**: 休憩検証を拘束時間ベースの不等式に統一、途中付与制約の追加、`member.birth_date` の追加と年少者ルールの実装（深夜22:00-05:00禁止、1日8h・週40h上限）。

### [F-P0-06] 深夜労働の境界ロジックと所属日・通算の矛盾（REQ-LABOR-002）

**事象**:
1. 深夜帯 `[22:00, 05:00)` は一般的に正しいが、**労基法第37条第4項は「厚生労働大臣が必要であると認める場合に午後11時〜午前6時」とする地域・期間指定の例外**を規定（現行運用では全国22:00-05:00だが、仕様に時間帯を定数ではなく設定値とする設計がない）。
2. **「基発第150号」の引用誤り**: 仕様は「昭和63年3月14日基発第150号」を、①暦日跨ぎ継続勤務の所属日（昭63.1.1基発第1号・婦発第1号）、②端数処理（昭和63年3月14日基発第150号）の双方に流用している。出典番号と内容の対応が曖昧。**法令引用の正確性は監査証跡として致命的**であり、条文・通達番号は社労士確認の上で個別に正しく記載し直す必要がある。
3. **所属日（始業日）の扱い**: 継続勤務は始業日の勤務として日次8h枠を通算するが、**割増賃金の「休日」判定（暦日基準）と「所属日」判定（始業日基準）の二元構造**が、通常日→法定休日跨ぎと法定休日→通常日跨ぎで対称に定義されているか不明（仕様は前者のみ記述）。**法定休日→翌通常日（日曜22:00〜月曜06:00）**の月曜0:00以降の扱いが未定義。
4. **深夜帯と休憩の按分**: 「22:00境界に跨る休憩は深夜該当部分のみ按分控除」とあるが、**休憩が深夜/非深夜どちらの労働から控除されるか**の配分規則（休憩の時間位置そのままの積集合で控除）を明示すべき。
5. **サマータイム/閏秒/タイムゾーン**: 日本は固定UTC+9で問題ないが、`TIMESTAMPTZ` と `TIME` 型の混在でサーバーTZ依存のバグ（`Asia/Tokyo` 固定）を防ぐ明示がない。MySQLの `TIMESTAMP` は2038年問題があり、`DATETIME` + 明示TZ変換の方針が必要。

### [F-P0-07] 端数処理規定の法的誤解と矛盾（REQ-LABOR-003 処理3）

**事象**:
1. **基発第150号の端数処理は「1か月における時間外・休日・深夜の割増賃金の総額に1円未満の端数が生じた場合、50銭未満切捨て・50銭以上切上げ」**であり、「各手当項目別」の記述は概ね妥当だが、**1時間当たりの賃金額・割増賃金額の端数処理（1円未満切上げ/四捨五入）**および**1か月の時間外労働時間数の合計の30分未満切捨て・30分以上1時間切上げ**（通達で認められる便宜上の措置）との**関係が未規定**。本仕様は秒単位完全精度を採用しており、**労働者に有利な処理であるため適法**だが、「30分切捨て」を行わないことを**明示的な設計判断**として記録すべき。
2. **本仕様の端数処理は労働者不利益方向を含む**: 項目別HALF_UPは通達許容範囲内だが、**割増賃金「総額」ではなく「項目別」に丸めると、合計で最大1.5円の差異**が生じ得る。通達は「総額」への適用を想定しているため、**項目別丸めが通達適合か社労士確認が必要**（現仕様は通達の拡大解釈）。
3. **月給制でないため問題ないが、基礎賃金に含めるべき手当**（皆勤手当、役職手当等、交通費は除外可）の算入規定がない。時給のみ想定なら明示的に限定宣言すべき。
4. **「基本給 = 総実労働時間 × 時給」の端数処理が未定義**（本文は基本給と通勤手当を「別個に確定」とあるが丸め規則なし）。
5. 分子累計方式 `hourlyWage × seconds × rateFactor`、共通分母 `3600×100` は妥当だが、**休日35%・深夜25%・残業25%/50%の「率」はBigDecimalで有理数管理**するという要件と、整数rateFactor（25,35,50,60,75）の方式が併記され**実装方針が二重化**している。
6. **REQ-LABOR-001 の `divide(60, 10, HALF_UP)`（scale=10）と REQ-LABOR-003 のBigInteger分子累計は互いに矛盾**。前者は丸めを含む中間値を出力（`overtimePayExact`）しており、これを月次集計に連携すると**スケール10丸め誤差が累積**する（1/60 は循環小数）。→ 月次連携は分子/分母ペアで行い、`overtimePayExact` は参考表示値とすべき。

### [F-P0-08] 給与確定トランザクションの仕様誤り（REQ-LABOR-004）

**事象**:
1. **`SET LOCAL lock_timeout = '3s'` は PostgreSQL 構文**であり、MySQL 8.4（Target Architecture）では無効。MySQL では `SET SESSION innodb_lock_wait_timeout = 3`、または `FOR UPDATE NOWAIT` / `SKIP LOCKED`。**仕様内でMySQL/PostgreSQL構文が混在**し実装不能。
2. **悲観的ロックの粒度過大**: `store` 行ロックを給与確定中に保持すると、**当該店舗の全打刻・シフト・スタッフ承認がブロック**される。繁忙時間帯に精算を実行すると**店舗の打刻不能（可用性障害）**。精算は月次バッチで夜間実行等の運用制約がないと、**打刻不能＝労働時間記録義務違反リスク（労働安全衛生法第66条の8の3 ／ 労働時間の客観的把握義務）**につながる。→ 精算期間の凍結は「ロック」ではなく**対象期間の打刻を「締め」状態にし、期間外（翌月分）打刻は許可**する設計に変更すべき。
3. **ロック階層「store → store_staff → payroll_settlement」と REQ-SHIFT-001/002 のロック順序（store_staff のみ、または member_id 行ロック）の整合が未検証**。REQ-SHIFT-002 は `store_staff` ロックから開始し `store` ロックを取らないため、**給与確定（store→store_staff）と並行すると、順序は整合するが、REQ-SHIFT-002 の「member_id 対象行ロック」が複数店舗の `store_staff` を逆順取得**した場合にデッドロックの可能性。複数 `store_staff` の取得順序（ID昇順固定）規定がない。
4. **「打刻の凍結」が店舗ロックのみで保証される主張は誤り**: 打刻 INSERT が `store` 行を FOR UPDATE していなければ、InnoDB の通常 INSERT は店舗行ロックによってブロックされない（外部キーの共有ロックは `FOR UPDATE` 排他ロックと競合しブロックされるが、**FKチェックの挙動に依存する暗黙の仕様で脆弱**）。REPEATABLE READ のスナップショットでは**ファントム打刻が精算スナップショット後にコミット**され得る。→ 明示的な `attendance_period_lock` テーブル、または精算開始時の `status='CLOSING'` 状態と打刻側のチェックを仕様化すべき。
5. 初回確定時の `OPEN` ヘッダー INSERT 後、**計算途中でクラッシュした場合のOPEN残骸**の扱い（冪等再開・タイムアウト回収）が未定義。
6. `payroll_settlement_line` 永続化とヘッダー CAS 更新が**同一トランザクションか**が明記されていない（部分コミットの危険）。
7. **月次総支給の最低賃金補正の差額記録**が「監査イベント発行」とあるが、**イベントの永続化先・再送保証（Outbox）**がない。

### [F-P0-09] 最低賃金法第4条対応の仕様欠陥（REQ-LABOR-001 処理6、REQ-STAFF-002）

**事象**:
1. 最低賃金は**地域別（都道府県）・産業別（特定最低賃金）・改定日（毎年10月前後、年度により発効日が異なる）**で変動する。`prefectureCode` はあるが、**最低賃金マスタ（都道府県・発効日・金額・種別）のエンティティが未定義**。
