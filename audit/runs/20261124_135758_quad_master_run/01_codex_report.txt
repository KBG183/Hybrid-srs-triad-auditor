**判定は修正後採択を勧告します。** 最優先で是正すべき箇所は RFC-SYS-01 です。提案されたフィルタをそのまま適用すると、必須ドキュメントを削除したPRが検証をパスしてしまう脆弱性があります。また、RFC-FUNC-04 も共通規約で許容遷移を確定する前にはマージ遮断ルールとして配備することは困難です。

| 提案 | 設計判断および失敗リスク | 具体的な修正勧告 |
|---|---|---|
| **SYS-01 · 動的CI検証** | 対象一覧を単一真実に統合する方向性は妥当です。ただし `required == true` とファイル存在を同時に選別条件として用いると、必須ファイルの欠落が成功として扱われます。 | 設定をパースし `required` が JSON boolean であることを検証した上で、必須一覧を確定してください。各必須パスの存在有無は別個の合格条件として検証してください。空の必須一覧、欠落ファイル、検証器実行失敗をすべてCI失敗として集計し、対象別結果を出力してください。PowerShellでは呼び出し直後に `$LASTEXITCODE` を保持し、最終ファイルの成功が先行失敗を覆い隠さないようにしてください。 |
| **SYS-02 · 初案自動ステージング** | `git add` は検証済み初案をインデックスに保全する上で有用です。ただしインデックス項目は後続の `git add` や `reset` で改変される可能性があり、既存ファイルの変更を上書きするリスクがあります。 | 自動化が所有する新規出力パスへ適用範囲を限定してください。既存パスに未コミット変更が存在する場合は上書き前に中断してください。リポジトリ基準のリテラルパス1件のみをステージングし、インデックスのBlobが検証対象と合致することを確認して成功を記録してください。 |
| **FUNC-03 · DDLメタデータ抽出** | 構造化メタデータはカラム数の根拠となります。最も危険なケースは、抽出器が複合FK、ネストされたCHECK、文字列中のカンマを誤解釈したまま正常終了することです。この時 `IMMUTABLE` 表記は誤答の権威を高めてしまいます。 | リポジトリのSQL方言を明示し、正規表現を維持する場合は字句解析器でコメント・クォートを除去した上で解析してください。列数は抽出した列リスト長から算出し、複合キーの列順序とFK参照先を保持してください。スキーマハッシュとメタデータを併せて注入し、抽出失敗時は初案生成をFail-Closedで中断してください。 |
| **FUNC-04 · FSMおよびロック順序** | RFCの `SUBMITTED → CONFIRMED → REJECTED` 表記は `CONFIRMED → REJECTED` も許容すると読めます。実際が `SUBMITTED` から2状態へ分岐するなら、この例示自体が誤った規則の源泉となります。ロック規則も全体順序と部分ロック取得を区別する必要があります。 | 共通規約に許容遷移 `(from, to)` とロック順位を有向グラフとして厳密定義してください。リンターは部分ロック取得（例: store と store_staff のみ）を許容し、実際の取得順序の逆転（Inversion）のみを遮断してください。既存ドキュメントでの誤検知を確認した上で `[FATAL]` に昇格してください。 |
| **GOV-05 · コミット後残余差分** | `working tree clean` を絶対条件とする際、コミット処理自体が追跡ファイルを変更して差分を残す問題を遮断する必要があります。 | 完了条件を「コミット処理が追加で作成した残余差分が0件」と定義してください。追跡するマニフェストはコミット前にステージングされた入力から生成し、フックは一致有無を読み取り専用で検査してください。フックに `-NoLog` を導入し、検証実行自体によるログファイル更新差分が残らない構造を確立してください。 |
