Audit Report: KINTAI Pre-Commit Hard-Gate Architecture

**Scope note:** The referenced `scratch/audit_bundle_gate.ps1` was not included in the bundle. This audit covers TARGET 1 (`pre-commit`) and TARGET 2 (`verify_repo_total_integrity.ps1`) as supplied. Where the spec's own self-description (header says 5 checks, section banners say 5/5 and 5/8, body implements 8) conflicts with the code, I treat the code as authoritative and flag the drift.

---

1. Executive Summary

The design intent (layered, deterministic, fail-closed) is sound, but the implementation contains several defects that make the gate **unreliable in both directions**: it will produce **false blocks** (ordinary <USER_HOME> doc mentions, `[ -z ]` author logic, bare-IP matches) and **false passes** (working-tree vs. index mismatch, BOM/encoding blind spots, `-notmatch`-style logic gaps, silent exe-missing paths). Two findings are release-blocking: **the gate scans the working tree rather than the staged blob**, and **the Korean/sensitive checks can silently fail open**.

2. Findings Table

| ID | Item | Severity | Verdict | Evidence | Analysis |
|---|---|---|---|---|---|
| F-01 | Staged-diff grep drops all added lines except those with a space after `+` | **Critical** | FAIL | `grep '^+ '` | With `--unified=0`, an added line is `+<content>` with no mandatory space. Only lines whose content *begins with a space* match. Lines starting with a non-space character (e.g. `+<PRIVATE_IP_C>1.5`, `+password=...`, `+<USER_NAME>`) are discarded before the sensitive scan. This is a **fail-open on the primary secrets gate**. Fix: `grep '^+' \| grep -v '^+++'`. |
| F-02 | `grep -v '^+++'` also removes legitimate added lines | High | FAIL | `grep -v '^+++'` | Any added line whose content starts with `++` (e.g. `++i;`, markdown `+++` TOML front-matter) is stripped and evades scanning. Anchor to the diff file header instead: exclude `^+++ [ab/]` / `^+++ /dev/null`. |
| F-03 | Working-tree scan instead of index scan (TOCTOU / partial staging) | **Critical** | FAIL | `grep -P ... "$FILE"` (hook); `git ls-files` + `ReadAllLines($f)` (PS1) | Both read the working copy. With `git add -p`, or edits made after staging, the committed blob differs from what was scanned. A developer can stage a Korean/sensitive version, revert the working tree, and the gate passes clean content while committing dirty content (and vice versa: false blocks). Fix: read blobs via `git show :"$FILE"` / `git cat-file blob`. |
| F-04 | Unquoted `for FILE in $STAGED_FILES` word-splitting | High | FAIL | `for FILE in $STAGED_FILES` | Filenames with spaces split into fragments, which then fail `grep` (no such file, stderr suppressed) and **count as clean**. Additionally, `core.quotepath` default octal-escapes non-ASCII paths (e.g. Korean filenames come out as `"\355\225\234..."` with quotes), so the path never resolves and the file is silently skipped. Fix: `git diff --cached --name-only -z` + `while IFS= read -r -d ''`, and `-c core.quotepath=off`. |
| F-05 | `grep -P` failure is indistinguishable from no match (fail-open) | **Critical** | FAIL | `grep -P ... > /dev/null 2>&1` then `if` | `grep` exits 0=match, 1=no match, 2=error. The `if` treats any non-zero as "clean". Causes of exit 2: `-P` unsupported (Git-for-Windows `grep` built without PCRE, macOS BSD grep), invalid `\x{...}` syntax under a non-UTF-8 locale, unreadable/missing file. **The Korean gate can silently disable itself.** Also, `\x{1100}` in PCRE requires UTF mode; under `LC_ALL=C` it errors or matches bytes. Fix: pin `LC_ALL=C.UTF-8`, check `$? -eq 2` → block, and add a self-test canary at hook start. |
| F-06 | Hook shebang is wrapped in a PowerShell block comment | High | FAIL | `<# #!/bin/sh ... #>` | As written, the hook file begins with `<#`, so `#!/bin/sh` is not the first two bytes. Git on POSIX will not honor the shebang (exec format error → hook **skipped with a warning, commit proceeds**). Git-for-Windows uses its bundled sh, which may tolerate it, masking the issue on dev machines but not on Linux/macOS/CI. The `#>` terminator is also dead/invalid shell text. Presumably a spec-rendering artifact; if it is literal, it is a bypass. Verify the on-disk first bytes. |
| F-07 | Hook is not installed by the repo; `core.hooksPath` unset by default | High | WARN | `.git/hooks/pre-commit` path | `.git/hooks` is untracked and per-clone. New clones, worktrees, and CI have **no gate**. The "auto-wiring" is a convention, not an enforcement. `git commit --no-verify` bypasses entirely. Mitigation: tracked `.githooks/` + `git config core.hooksPath`, plus an equivalent **server-side/CI required check** (pre-receive or PR status) as the true hard-gate. |
| F-08 | Author gate uses `GIT_AUTHOR_IDENT` that is overridable, and logic is brittle | Medium | WARN | `sed -n 's/.*<\(.*\)>.*/\1/p'`; `[ -z ... ]` | `GIT_AUTHOR_EMAIL`/`--author` env/flag override the check target trivially, and committer identity is ignored. If `user.email` is unset and `useConfigOnly` is off, `git var` may fail or synthesize a hostname-based address (e.g. `user@host.local`) that passes. The check blocks only the single literal `test@test.local`. It is an advisory heuristic, not an identity control; do not describe it as "verification". |
| F-09 | Sensitive-pattern drift between hook and PS1 | High | FAIL | Hook: `<USER_HOME>`, `<USER_HOME>`, `<TAILSCALE_IP>`, `<TAILSCALE_IP>`, `<TAILSCALE_IP>`, `<PRIVATE_IP_C>`; PS1 (base64): `<TAILSCALE_IP>`, `<TAILSCALE_IP>`, `<TAILSCALE_IP>`, `<PRIVATE_IP_C>`, `<USER_NAME>`, `<MASKED_TAG>`, `<MASKED_TAG>`, `<MASKED_TAG>` | Different lists: the hook blocks `<USER_HOME>` paths, the PS1 does not; PS1 pattern lacks a trailing-dot anchor so it matches version/number strings (false positives), while the hook is stricter. Two sources of truth guarantee divergence. Centralize in one file consumed by both. Note the base64 obfuscation protects nothing meaningful (trivially decoded) yet hinders review. |
| F-10 | `C:\\Users` regex semantics in hook | Medium | WARN | `'(…\|C:\\Users\|…)'` under `grep -E` | In ERE, `\\` matches one literal backslash, so this works, but it will also block legitimate documentation/test fixtures mentioning `<USER_HOME>`, with no allowlist mechanism in the hook (the PS1 allowlists by filename `VerifySRS_Integrity.cs`/`pre-commit`, the hook does not). The hook itself contains the patterns, so **committing a change to the hook triggers its own gate** (self-block). Needs an allowlist/path exclusion. |
| F-11 | PS1 sensitive-pattern allowlist is a substring `-notmatch` on path | Medium | WARN | `$f -notmatch 'VerifySRS_Integrity\.cs' -and $f -notmatch 'pre-commit'` | Unanchored: any file whose path merely *contains* `pre-commit` (e.g. `docs/pre-commit-notes.md`, `secrets_pre-commit.txt`) or `VerifySRS_Integrity.cs` is exempt from the leak scan. Attackers/accidents can exploit by naming. Anchor with exact normalized paths. Also, the exemption applies only to the leak counter, not the Korean counter. |
| F-12 | Korean gate: `_KO.` exemption is a substring match on full path | High | FAIL | Hook: `grep -qE '_KO\.'`; PS1: `-match '_KO\.\|_ko\.'` | Unanchored and matches directory names too: `src/foo_KO.bar/anything.md` or `data_ko.v2/secret.cs` is exempt wholesale. Hook is case-sensitive (`_KO.`), PS1 is mixed (`_KO.`/`_ko.`), so `Readme_ko.md` is exempt in PS1 but **blocked** by the hook, a behavioral split. Restrict to basename suffix `_KO.<ext>` and make both layers identical. |
| F-13 | Korean character-class coverage gaps | Medium | WARN | Hook ranges: 1100–11FF, 3130–318F, A960–A97F, AC00–D7A3, D7B0–D7FF; PS1 equivalent via `\u` | Omitted: Hangul Compatibility/halfwidth forms **FFA0–FFDC** (halfwidth Hangul), enclosed/circled Hangul **3200–321E, 3260–327E**, and Hangul syllables presented in **U+3200 block**. Halfwidth Hangul letters (U+FFA0–FFDC) are a known filter-evasion vector. Also **Hangul filler U+3164 / U+115F/1160** (invisible) are in-range but benign-by-design; fine. Add FFA0–FFDC and 3200–321E/3260–327E. |
| F-14 | Non-UTF-8 and UTF-16 files evade the Korean scan | High | FAIL | Hook `grep -P` on raw bytes; PS1 `ReadAllLines($f, UTF8)` | CP949/EUC-KR-encoded files contain no valid UTF-8 and are not matched under a UTF-8 pattern (and grep may treat them as binary: "Binary file matches", which still returns 0 but output is suppressed; behavior locale-dependent). UTF-16 files are mis-decoded by the PS1 UTF-8 reader, producing garbage with interleaved NULs, so **Hangul silently passes**. Add detection of non-UTF-8/UTF-16 BOM and block or transcode. |
| F-15 | Binary-extension skip list is a bypass vector | High | FAIL | `'\.(exe\|dll\|png\|jpg\|ico)$'` | Renaming a text file to `.png`/`.ico` skips Korean, sensitive, and BOM scans entirely; also unlisted binaries (`.zip`, `.pdf`, `.docx`, `.xlsx`, `.pdb`, `.so`) are fully scanned as text via lossy UTF-8 decoding, producing false negatives and noise. Use `git diff --numstat`/`file`/`-I` heuristics (NUL-byte detection) rather than extension trust. Case-sensitivity also: `.PNG`, `.EXE` match? PowerShell `-match` is case-insensitive (OK); hook has no such skip. |
| F-16 | UTF-8 BOM check scope mismatch and `-Raw` blind spots | Medium | WARN | Check 6: `ReadAllBytes`, first 3 bytes | Only a leading BOM is detected. Embedded BOMs/U+FEFF mid-file (from concatenation) pass. UTF-16 LE/BE BOMs (`FF FE`/`FE FF`) and UTF-32 BOMs are **not flagged**. The exemption list excludes `.exe/.dll/.png/.jpg/.ico` but BOM scan still runs on all other binaries (harmless, but a binary starting with EF BB BF produces a false positive). The hook has **no BOM check at all**; BOM detection happens only in the slow PS1 layer. Also note: ReadAllLines with `[Text.Encoding]::UTF8` strips a BOM transparently, so Checks 1/8 are **BOM-blind**, which is consistent but means BOM'd `CURRENT_STATUS.md` is judged only on the byte check. |
| F-17 | Check 8 (single health line): CRLF/trailing-whitespace and detection logic | Medium | WARN | `^- \*\*<ja-label>\*\*:` ; `$healthLineCount -ne 1` | (a) The label is encoded as a hand-built byte array to dodge the Zero-Korean rule — but the label is **Japanese**, a deliberate evasion that the Korean gate was never designed to catch, and also means the real file contains non-ASCII text in a "public" file; this is a policy inconsistency, not a bug. (b) Indented/`*`-bullet/`1.`-numbered or differently-spaced variants (`-  **label**:`, `* **label**:`, label followed by space before colon) are **not counted**, so duplicates slip. (c) Duplicate inside a fenced code block counts as a health line (false positive). (d) `if (Test-Path $csPath)` — **missing file is a silent PASS** (no else), so deleting the file defeats the gate. |
| F-18 | Check 3 (dashboard) logic is regex-fragile and one-sided | Medium | WARN | `'REQ-LABOR-001.+\|\s+\*\*PASS\*\*\s*\|'` | `.` doesn't match newlines (single-line by default), so a PASS split across lines evades. It only forbids PASS for **one hardcoded requirement ID** and then requires the substring `Claude 5.5` anywhere in the document (even in prose). Hardcoded business ID in a generic gate = brittle, and the check asserts a *desired status* rather than verifying consistency against the ledger as its title claims ("Dashboard vs Audit Ledger"): **the ledger is never read**. Also `ReadAllText` on a missing `pipeline_metrics.md` throws (see F-19). |
| F-19 | `$ErrorActionPreference = 'Stop'` absent in the gate script itself | **Critical** | FAIL | Check 7 mandates it for `tools\scripts\*.ps1`; `verify_repo_total_integrity.ps1` contains no such line | The script **violates its own Check 7** (it lives in `tools\scripts`). Consequence: a terminating exception (e.g. missing `pipeline_metrics.md`, unreadable file) may still end the script with a non-zero code, but non-terminating errors (failed `git ls-files`, failed `Test-Path`, `Get-ChildItem` errors) are swallowed, and checks proceed against empty data, yielding **"ALL PASS" on zero files**. Note also that when the scan reports "0 files", it still prints PASS. Add `Set-StrictMode`, `$ErrorActionPreference='Stop'`, and a precondition `trackedFiles.Count -gt 0`. |
| F-20 | Exit-code propagation: `$?`-after-`echo`, no `set -e`, and `powershell.exe -File` semantics | High | WARN | `... ; if [ $? -ne 0 ]` ; `powershell.exe -File ...` | Pattern is correct as written (`$?` read immediately), but fragile: any edit inserting a statement between command and test breaks it. More important: `powershell.exe -File` returns **1 on unhandled terminating errors**, but a script that ends via `exit N` returns N; **script parse errors, missing script file, and execution-policy/AppLocker/Constrained-Language failures return non-zero** (good). However if `powershell.exe` is not on PATH (Linux/macOS/non-Windows CI, WSL without interop) the shell returns 127, the hook blocks, which is a safe failure but renders the repo **uncommittable on non-Windows**, creating a social incentive to `--no-verify`. Also Git-for-Windows MSYS path conversion can mangle arguments; here the args are relative paths so OK. |
| F-21 | `-ExecutionPolicy Bypass` and unsigned invocation | Medium | WARN | `powershell.exe -ExecutionPolicy Bypass -File ...` | Weakens the host's script-signing posture for the entire gate, and any local modification of the PS1 (which is itself tracked and editable in the same commit) executes without integrity check. **The gate is mutable by the person it constrains**: a committer can edit `verify_repo_total_integrity.ps1` / `VerifySRS_Integrity.exe` in the same commit to weaken checks, and the *new* weakened version is what runs. Needs out-of-band trust (CI uses protected-branch copy / hash pin). |
| F-22 | Binary verifier `VerifySRS_Integrity.exe` and `TestV52Suite_Regression.exe` are opaque, tracked, unverified | High | FAIL | Hook step 5; Check 5 | Checked-in executables are run as the **root of trust** with no hash/signature pinning; supply-chain and tampering risk. The Check 5 label says "11/11" but verifies only the **exit code**, not that 11 tests ran (an exe that always `exit 0`, or crashes after printing nothing, passes). If the exe is absent, `& $regExe` throws a terminating error only under `Stop` (see F-19), otherwise `$LASTEXITCODE` retains a **stale prior value** (likely 0 from an earlier call) → **false PASS**. Same stale-`$LASTEXITCODE` hazard in Check 2. |
| F-23 | Stale `$LASTEXITCODE` and unchecked `git ls-files` | High | FAIL | Check 1 `git ls-files`; Check 2 loop | `$trackedFiles = git ls-files` is never validated: if `git` fails (not a repo, `safe.directory` ownership error in CI/containers), the variable is empty, Check 1 and Check 6 iterate zero files and print "PASS: 0 ... across 0 files". Output of `git ls-files` is also subject to `core.quotepath` mangling for non-ASCII/space paths and **splits on newlines only** (OK) but returns quoted escaped paths that `Test-Path` cannot resolve → `continue` → **file silently skipped**, including Korean-named files (the exact artifacts most likely to contain Korean). |
| F-24 | Checks 1 & 6 scan the full tracked tree on every commit (performance) | Medium | WARN | `ReadAllLines` per file in a PowerShell loop; `ReadAllBytes` of every file for BOM | O(repo size) per commit. `ReadAllBytes` loads entire files (including large logs/ledgers) just to read 3 bytes; line-by-line PowerShell `-match` over every line is orders of magnitude slower than `grep -P`. Startup of `powershell.exe` (~0.4-1 s) plus three launches of exes per ledger (Check 2 launches the integrity exe **5×**) plus the regression suite. Expect multi-second to tens-of-seconds latency as logs grow (the ledgers are append-only), which is the primary driver of `--no-verify` culture. Mitigation: scope pre-commit to staged files, run full scan in CI/nightly; read only first 3 bytes via `FileStream`; use `[IO.File]::ReadLines` + compiled `[regex]`; cache by blob hash. |
| F-25 | Hook already scans staged content once; PS1 repeats full scan (duplicate work, divergent semantics) | Medium | WARN | Hook steps 3-4 vs PS1 Check 1 | Same two policies enforced twice with *different* implementations (grep -P on working tree vs .NET regex on working tree, different exemptions, different pattern lists, see F-09/F-12). Duplication multiplies cost and creates ambiguous authority: a commit can pass layer A and fail layer B (or the reverse). Pick one implementation, parameterize scope. |
| F-26 | Spec drift: "5 checks", "[Check n/5]", "[Check 5/8]", "(8 Checks)" | Low | WARN | `.DESCRIPTION` lists 5; banners show `1/5`–`4/5`, then `5/8`–`8/8` | Cosmetic but audit-relevant: the documentation contract (SRS traceability) says 5, the code runs 8, and the description's item 2 ("Zero-Korean") is actually folded into Check 1 while description items 3-5 map to Checks 2-4. Hard-gate documentation should be generated from the implementation to prevent drift. |
| F-27 | PS1 exits via `exit 1`/`exit 0` only at the end; uncaught early `exit` / `return` paths and `Write-Host`-only reporting | Low | WARN | Final block | Logic is acceptable, but all diagnostics go through `Write-Host` (information stream, not capturable/redirectable in some hosts), so CI logs and `2>&1` capture in the hook lose them. Prefer `Write-Output`/`Write-Error` for machine-parsable results, and emit a final machine-readable summary (JSON/exit-code map) rather than color text. |
| F-28 | `Split-Path` project-root derivation and CWD dependence | Medium | WARN | `$projectRoot = Split-Path -Parent (Split-Path -Parent $scriptDir)` ; relative `git ls-files` paths | `git ls-files` returns repo-root-relative paths, but `Test-Path $f` / `ReadAllLines($f)` resolve against the **process CWD**, not `$projectRoot`. When the hook runs from the repo root it works; when invoked from a subdirectory, a git worktree, a submodule, or a GUI client with a different CWD, **every `Test-Path` fails and every file is skipped**, producing a vacuous PASS (compounded by F-19/F-23). Also, `[IO.File]` APIs use `[Environment]::CurrentDirectory`, which can differ from PowerShell's `$PWD`. Always `Join-Path $projectRoot $f`. Also `$projectRoot` derivation assumes `tools/scripts/` depth. |
| F-29 | Merge/rebase/amend/CI contexts | Medium | WARN | Pre-commit only | Pre-commit does not run for `git merge` (no-conflict fast paths, `-X`), `git pull --rebase` replays, `cherry-pick` (it does run for the final commit, but replays apply **without** per-commit staged-diff semantics), `git commit --amend` with `--no-edit`, `git revert`, or any push from another clone without hooks. Large merges produce giant diffs through the `STAGED_DIFF` shell variable (ARG_MAX/memory), and `echo "$STAGED_DIFF"` can mangle backslashes/leading dashes (`echo -e` semantics in dash/busybox; use `printf '%s\n'`). |
| F-30 | `echo "$STAGED_DIFF"` leaks sensitive matches into terminal/CI logs | Low | WARN | `echo ... \| grep -E ... \| head -n 5` | On block, the offending sensitive strings are printed to the console (and CI logs, which are often more broadly readable than the repo). This leaks the very secrets/identifiers the gate protects. Print only file:line and pattern name, with redaction. |
