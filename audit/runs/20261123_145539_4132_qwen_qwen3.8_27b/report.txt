### Adversarial Simulation Narrative

The target specification has successfully addressed the critical operational deadlocks identified in previous audits.

1.  **Resignation Access Paradox (Resolved):** Previously, a strict interpretation of `employment_status = RESIGNED` would block any API call associated with that member, including the final clock-out. The new specification in `[REQ-STORE-004]` introduces a temporal exception. It recognizes that "Resigned" is a state that takes effect *after* the work is done, but the system must allow the work to be *recorded* before the state fully severs access. The inclusion of the "12:00 next day" grace period specifically addresses the Japanese labor context of night shifts (22:00-05:00) where a shift starting on the resignation day ends the next morning. Without this, the system would force a 403 error on the clock-out, resulting in unrecorded work and a legal wage dispute.

2.  **Wage Calculation Orphan (Resolved):** The risk of wage loss arises if the contract history is marked as "inactive" or "cancelled" in a way that excludes it from the wage calculation query. The specification in `[Section 4]` decouples the *wage handoff* from the *membership status*. It relies on the `effective_to` date boundary. By mandating that `effective_to` is set to `resigned_date + 1` (exclusive), the resignation date itself remains inside the valid contract window. The explicit instruction to ignore `employment_status` during handoff ensures that even if the status flips to `RESIGNED` immediately upon processing, the wage engine can still find the valid rate. This is a robust design that prevents the "zero wage" bug.

3.  **Idempotency Deadlock (Resolved):** In distributed systems, `POST` requests are not inherently idempotent. If a user clicks "Resign" and the network hangs, the client might retry. If the first request succeeded, the second request would find the user already `RESIGNED`. A naive implementation would return 409 (Conflict) or 400 (Bad Request), signaling an error. The specification in `[REQ-STORE-003]` explicitly defines the behavior for this exact case: if the date matches, return 200 OK. This "safe retry" pattern is crucial for user experience and prevents support tickets related to "failed resignation" errors that are actually successful operations.

No new P0 or P1 defects were found in the revised specification. The logic is consistent, handles the temporal boundaries of Japanese labor law (night shifts, resignation dates), and provides clear idempotency guarantees.
