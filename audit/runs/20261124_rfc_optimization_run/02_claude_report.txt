# RFC-008 アーキテクチャレビュー

## 総評
Zero-Regression を優先して「構成は動かさず、文書と責務定義を整える」方針は妥当です。ただし、(a) 責務マトリクスに網羅性と排他性の欠落があり、(b) パス安全性の主張が根拠不足で、(c) 将来のドリフトを防ぐ機構がありません。承認前に修正すべき点があります。

---

## 1) ディレクトリ責務境界

**良い点**
- 11領域ごとに責務、ファイル数、ガバナンス規則を表にしており、可視性は高いです。
- `governance/`(憲法)、`queue/`(フェイルクローズドゲート)、`approved/`(署名付きマニフェスト)は役割が明確に分離されています。

**指摘事項**
1. **「全資産を11領域に分類」は事実と合致しません。** `README.md`、`GEMINI.md`、`.gitignore` など、ルート直下のファイルがどの領域にも属していません。§4 で `GEMINI.md` を更新対象にしているのに、責務表に所在がありません。ルート直下ファイルの扱いを定義してください。
2. **監査関連の置き場が重複しています。** `audit/`(実機ログ・静的レポート)、`logs/`(監査台帳)、`docs/`(トレーサビリティ文書)、さらに旧 `docs/audit_runs/` が並存し、「どの種類の監査成果物をどこに置くか」の判定基準がありません。
3. **正本の優先順位が未定義です。** `governance/`(最上位ルール)、`config/`(SSOT・Track 1/2 正本)、`approved/`(承認済み)で正本性の主張が競合します。矛盾時の優先順位(憲法 > SSOT > …)を明記すべきです。
4. **数値に整合しない箇所があります。**
   - `logs/` は CSV 5 + MD 3 = 8 に対し追跡ファイルが 10 件で、残り 2 件が不明です。
   - `finalize_daily_ledgers.ps1` は「6大台帳」とされ、8台帳という記述と合いません。
   - `governance/` 2 件のうち 1 件しか記載がなく、`config/` 5 件も `srs_targets.json` 以外が不明です。
5. **`metrics/` の「ロックファイル」を追跡対象としている点は不自然です。** 実行時生成物なら `.gitignore` 対象とするか、追跡の理由を明記してください。
6. **「ツール類の平坦な配置」を課題に挙げながら、`tools/`(42件)の再編案がありません。** 実質は文書更新のみのため、タイトルの「最適化」は過大です。少なくとも将来の再編方針と、再編時の互換シム(エイリアス)方針を示すべきです。

---

## 2) CI/CD のゼロリグレッション安全性

**良い点**
- 5つのカノニカルエントリポイントを固定する方針は適切です。
- Phase B を文書のみに限定しており、実行パスへの影響は最小です。

**指摘事項**
1. **カノニカル一覧が不完全です。** 以下も強いパス依存を持つのに保護対象外です。
   - `config/srs_targets.json`
   - `approved/approval_manifest.json`
   - `queue/srs_pending_findings.json`
   - `governance/ARTICLE_0_SRS.md`
   - `audit/runs/`
   - `.github/workflows/ci.yml`
   - Git フックの配置先
   - `pipeline_draft_and_integrate.ps1`(`metrics/` に書き込むのに一覧にありません)

   「保護パス = 全ゲートが参照するパス」を機械的に導出して一覧化すべきです。
2. **`docs/audit_runs/` の無害性は主張のみで、検証がありません。** 「`.gitignore` 済みなので影響なし」としていますが、`.gitignore` は Git の追跡に効くだけで、リンターのファイルシステム走査や glob には効きません。次を確認し、結果を RFC に記載してください。
   - VerifySRS やスクリプトが `docs/` を再帰走査しないこと。
   - 「過去24時間の監査ログ検証」が旧ディレクトリを拾わないこと。

   また、427件のローカル残置はクリーンクローンとの挙動差を生むため、削除かアーカイブの手順も示してください。
3. **憲法関連ファイルの改訂手順が不明です。** `GEMINI.md` の版数変更(v1.07)が `approved/` の署名・マニフェスト更新や VerifySRS のハッシュ検査の対象か確認が必要です。対象なら Phase B に署名手順を組み込む必要があります。
4. **Phase C の検証が弱いです。** 11大ゲートの全件パスは必要条件ですが、移行前後でパス参照集合が不変であること(依存グラフの diff)や、README の構成図が実ツリーと一致することを検証していません。
5. **バイナリの来歴が未記載です。** `VerifySRS.exe` は「単一チョークポイント」ですが、ビルド元、ハッシュ固定、ソースとの一致検証の記述がありません。

## 3) 将来の保守性保証

**指摘事項**
1. **ドリフト検知がありません。** v1.02 から実態が乖離した問題の再発防止策が、手動の README 更新だけです。README の構成図とファイル数を `verify_repo_total_integrity.ps1` で自動照合する新ゲートの追加を推奨します。
2. **ファイル数や「427件」などの揮発的な数値を規範文書に固定すると、すぐ陳腐化します。** 数値は自動生成の付録に分離するか、削除してください。
3. **トップレベルディレクトリを追加・改名・廃止する際の変更管理(RFC必須、CODEOWNERS、保護パスの更新)が未定義です。**
4. **`audit/runs/`(124件)の保持期間、ローテーション、アーカイブ方針がありません。** 24時間検証と長期蓄積の関係も不明確です。
5. **承認・署名の運用主体(誰が、どの鍵で)が示されていません。**
6. **「4重交差監査による無欠性」という表現は過大です。** LLM(Codex、Claude、Qwen)は非決定的なので、最終的な合否権限は決定論的な VerifySRS に置くことを明記してください。LLM の指摘は助言扱いとし、不合格の判定権限も VerifySRS 側に限定すべきです。
7. **ロールバック手順がありません。** Phase B/C で失敗した場合の戻し方を記載してください。

---

## 必須修正項目(優先順)
1. ルート直下ファイルの扱いを追加し、「全資産」の記述を訂正する。
2. `logs/` と「6大台帳」、各ディレクトリのファイル数の不整合を解消する。
3. `docs/audit_runs/` が検証系に影響しないことを実証し、削除またはアーカイブ方針を示す。
4. カノニカルパス一覧を、実依存から機械的に導出した完全版へ拡張する。
5. `GEMINI.md` 改訂時の承認・署名フローを明示する。
6. README と実ツリーの整合を検証する自動ゲートを Phase C に追加する。
7. 正本の優先順位、監査成果物の置き場の判定基準、変更管理規則を追記する。

方針は妥当ですが、事実記述の不整合と未検証の安全性主張が残っているため、現状のままの承認は不適切と判断します。
