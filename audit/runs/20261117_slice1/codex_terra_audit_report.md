| Severity | 項目 | 判定 | 推奨事項 |
|---|---|---|---|
| P0 | 任意ロール登録 | FAIL | `role` を公開会員登録入力として受け付けると、攻撃者が `ROLE_OWNER` を自己付与できます。登録経路をスタッフ用・オーナー作成用に分離し、ロールはサーバー側で固定してください。 |
| P0 | IDOR防御の実効性 | 要補強 | `SecurityContext` 利用方針だけでは不十分です。全ての店舗・所属・契約履歴APIで、認証済み `memberId` をトークン／Principalから取得し、リクエストのIDを信用せず、`store_id` と所属・所有関係をDB検索条件に必ず含めてください。 |
| P0 | 契約期間重複防止 | FAIL | `uq_contract_effective_from` は同じ開始日の重複しか防げず、期間重複は防げません。トランザクションと行ロック、またはDBトリガー等で、同一 `store_staff_id` の期間交差を拒否してください。 |
| P1 | `store.owner_id` 外部キー | 要明記 | `fk_store_owner` は `member(member_id)` を参照し、削除・無効化時の方針（通常は `RESTRICT`）をDDLで固定してください。オーナーロール保持・有効状態は単純なFKでは保証できないため、登録トランザクション内で検証が必要です。 |
| P1 | 店舗トークンの一意制約 | 要補強 | `invite_code` と `qr_token` にそれぞれ `UNIQUE NOT NULL` を設定してください。招待コードは衝突リトライだけでなく、失効・ローテーション・利用制限を定義する必要があります。QRトークンは平文保存ではなく、照合用ハッシュ保存も検討してください。 |
| P1 | メール一意性 | 要補強 | DBの単純な `UNIQUE(email)` は大文字小文字・Unicode正規化差異を防げません。正規化済みメール列を作成し、一意インデックスを設定してください。 |
| P1 | 所属マッピング制約 | 要補強 | `store_staff.store_id → store`、`member_id → member` のFKと、`UNIQUE(store_id, member_id)` を明記してください。ただし退職後の再雇用を許可するなら、この一意制約では再登録不能です。所属履歴化、または「在籍中のみ一意」の設計に変更してください。 |
| P1 | 雇用状態遷移 | FAIL | `PENDING → ACTIVE → RESIGNED` の遷移主体・前提・再雇用規則が未定義です。オーナーのみが承認／退職処理可能、`RESIGNED → ACTIVE` は禁止または再雇用フロー限定、といった遷移表を実装・テスト対象として定義してください。 |
| P1 | 退職後の権限・給与履歴 | 要補強 | `RESIGNED` 後は打刻・シフト閲覧更新・契約変更を拒否しつつ、確定済み給与と履歴の閲覧監査を維持する必要があります。退職日、最終契約終了日、未確定精算の扱いを定義してください。 |
| P1 | 所属申請時の賃金改ざん | 要補強 | スタッフ本人が `initialHourlyWage` や交通費を指定できると、承認処理の不備で不正契約が成立し得ます。申請と契約条件確定を分離し、賃金条件は所有者権限でのみ確定してください。 |
| P1 | 契約更新の競合 | 要補強 | 有効契約を閉じて新契約を作る処理は、対象 `store_staff` と現行契約をロックした単一トランザクションで実施してください。同時更新時に複数の `effective_to IS NULL` が発生しないことを保証すべきです。 |
| P2 | `chk_contract_dates` | 要補強 | `effective_to > effective_from` に加え、`effective_from` のNULL禁止、賃金・交通費・月額上限の非負／正値チェックをDDLで明記してください。最低賃金判定は地域・適用日時に依存するため、定数ではなく履歴化された基準を参照する設計が望ましいです。 |
| P2 | パスワード保存列 | 要補強 | BCryptハッシュ用に十分な長さ（通常60文字以上、将来方式変更を考慮して255文字程度）の列を確保し、平文・復元可能暗号文・ログ出力を禁止してください。 |
| P2 | 招待コードによる列挙 | 要補強 | 無効招待コードと既存コードの状態差から店舗情報を列挙できないよう、エラー応答を最小化し、レート制限・試行監査・有効期限を設けてください。 |

総評として、基礎的なFK・複合一意制約の方向性は妥当ですが、現状では「ロール自己昇格」「API単位での所有／所属検証不足」「契約期間重複」の3点が本番投入を阻害するP0です。特に `uq_contract_effective_from` を「重複期間の完全防御」と見なすことはできません。
