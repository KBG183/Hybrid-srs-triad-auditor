### Interaction Matrix & Adversarial Simulation

**1. Rule Extraction & State Analysis**
*   **State Definitions**: `store_staff.employment_status` is strictly `PENDING`, `ACTIVE`, or `RESIGNED`.
*   **Termination Logic (REQ-STORE-003)**: Upon resignation, `employment_status` becomes `RESIGNED`, `resigned_date` is set, and `effective_to` of the final active contract is set to `resigned_date + 1`.
*   **Access Control (REQ-STORE-004)**: Staff business operations require `employment_status = ACTIVE`.
*   **Post-Termination Access (REQ-STORE-003/004)**: Staff can read their own contract history for dates where `joined_date <= asOf <= resigned_date`.
*   **Work Time Validation (Section 4)**: Work time is valid if `start <= end` and `real_work_time > 0`. It does *not* explicitly check `employment_status` in the provided snippet, but relies on the "Staff's normal business" scope defined in REQ-STORE-004.
*   **Wage Calculation Handoff (Section 4)**: Wage calculation uses the contract history determined by the "Japanese business day."

**2. Adversarial Simulation: The "Ghost Shift" & Wage Paradox**

*   **Scenario A: The Resignation Day Clock-Out (P1/P2 Risk)**
    *   **Context**: Employee `M1` resigns effective `2026-11-23`. `resigned_date` = `2026-11-23`.
    *   **Action**: `M1` clocks in at `09:00` and clocks out at `18:00` on `2026-11-23`.
    *   **System State**: At `18:00`, `employment_status` is `RESIGNED`.
    *   **Access Check**: REQ-STORE-004 states: "Staff's normal business is... limited to... `employment_status=ACTIVE`."
    *   **Conflict**: If the "Clock Out" or "Work Time Submission" endpoint is considered "normal business," it is blocked for `RESIGNED` users. However, the spec explicitly allows "resignation day's clock-in/out as legitimate work performance" in the Exception Handling of REQ-STORE-003 ("resignation day's clock-in/out is permitted as legitimate work performance").
    *   **Gap**: The spec *says* it is permitted, but does not define the *mechanism* to bypass the `ACTIVE` status check for the specific act of recording work time on the resignation day. If the API strictly enforces `ACTIVE` for *any* staff-scoped write operation (including time recording), the work is unrecorded. If it allows it, it must specifically exempt the `RESIGNED` status *only* for the date `resigned_date`. The current DDL/Spec does not show a specific flag or logic branch for "Resignation Day Work Recording" distinct from general staff operations. It relies on the reader inferring that "legitimate work performance" overrides the `ACTIVE` constraint. This is a **Silent Default (P6)** risk: If the implementation strictly follows REQ-STORE-004's `ACTIVE` requirement for all staff endpoints, the resignation day's work is rejected or lost.

*   **Scenario B: The Midnight Boundary & Wage Calculation (P3 Risk)**
    *   **Context**: `resigned_date` = `2026-11-23`. Contract `effective_to` = `2026-11-24`.
    *   **Action**: Employee works `2026-11-23 23:00` to `2026-11-24 01:00`.
    *   **Wage Calc**: Section 4 states wage calculation is based on the "Japanese business day."
    *   **Conflict**: The work spans two days. The contract is valid for `2026-11-23` (since `effective_to` is exclusive `2026-11-24`). Is the work from `00:00` to `01:00` on `2026-11-24` paid?
    *   **Analysis**: The contract `effective_to` is `2026-11-24`. This means the contract is valid *up to but not including* `2026-11-24`. Therefore, work performed on `2026-11-24` (even 1 minute) falls outside the contract period.
    *   **Result**: The employee is owed wages for `2026-11-23 23:00-24:00` (1 hour) but *not* for `2026-11-24 00:00-01:00` (1 hour) because the contract expired at midnight.
    *   **Legal/Operational Hazard**: In Japan, if an employee is scheduled to work past midnight, the contract must cover that time. By setting `effective_to` to `resigned_date + 1`, the system effectively terminates the employment relationship at midnight, potentially violating labor standards if the employee was *scheduled* to work past midnight on their last day. The spec does not address "scheduled work extending past resignation date." It assumes resignation ends all rights at midnight. If the employee worked 1 hour past midnight, that hour is "unrecorded work" or "unpaid work" because the contract no longer exists to calculate the wage.

*   **Scenario C: The 503 Retry & State Drift (P4 Risk)**
    *   **Context**: User accepts invitation. Server locks row. Another process rotates token. User gets 503.
    *   **Retry**: User retries.
    *   **Spec**: "Server... does not reuse store ID or membership state resolved in the preceding request."
    *   **Risk**: If the *first* request successfully created the `PENDING` row but failed to commit due to a timeout *after* the lock was acquired but *before* the response, and the client retries, the second request will find the `PENDING` row. This is handled.
    *   **However**: What if the first request *committed* the `PENDING` row, but the client received a 503 due to a network glitch *after* commit? The client retries. The second request finds the `PENDING` row. It checks expiration. If expired, it returns 410. If not, it proceeds to `ACTIVE`. This is correct.
    *   **Critical Gap**: The spec says "Lock acquisition failure is treated as 0 rows" in the *re-confirmation* step (Step 4 of REQ-STORE-002). But Step 3 says "Exclusively lock the membership row." If the lock in Step 3 fails (503), the transaction rolls back. The client retries. This is safe.

*   **Scenario D: The "Ghost Work" of Resigned Employees (P1 Blocked-Terminator)**
    *   **Spec Quote**: "Staff's normal business is... limited to... `employment_status=ACTIVE`."
    *   **Spec Quote**: "Resignation day's clock-in/out is permitted as legitimate work performance."
    *   **Contradiction**: The general rule (REQ-STORE-004) blocks `RESIGNED` users. The specific rule (REQ-STORE-003) allows clock-in/out on resignation day.
    *   **Implementation Ambiguity**: Does the "Clock In" endpoint check `employment_status`? If yes, it must have a special case: `IF status == RESIGNED AND today == resigned_date THEN ALLOW`.
    *   **Wage Calculation**: Section 4 says "Wage calculation... based on... contract history."
    *   **The Fatal Flaw**: If the employee resigns on Nov 23, and the contract `effective_to` is Nov 24, the contract is valid for Nov 23.
    *   **But**: What if the employee resigns *retroactively*? No, `resigned_date` must be `>= joined_date` and `<= today`.
    *   **What if the employee works *after* resignation?** The spec says "From the day after resignation... complete block."
    *   **The P0/P1 Finding**: The spec **does not define the API endpoint or logic for recording work time for a RESIGNED employee on their resignation day.** It only states the *business rule* that it is permitted. It does not specify *how* the system bypasses the `ACTIVE` status check in the authorization layer (REQ-STORE-004) for this specific case.
    *   **Consequence**: A standard implementation of REQ-STORE-004 will return `403 Forbidden` for a `RESIGNED` user attempting to clock out on their last day. The work is lost. This is a **P0** wage loss scenario.
