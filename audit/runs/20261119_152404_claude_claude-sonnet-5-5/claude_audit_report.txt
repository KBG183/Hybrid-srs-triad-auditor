# PROC-007 Cross-Audit Report: Orchestrator Self-Restraint Hard-Gate

**Auditor role:** Governance Auditor / Distributed Systems Safety Architect
**Scope:** Deadlock risk, mechanical detectability, bypass surface, operational resilience
**Spec under review:** v1.0.0-DRAFT (2026-11-19)

---

## 0. Executive Summary

PROC-007 targets real failure modes, and the instinct to move from *policy* to *mechanical enforcement* is correct. However, the draft has one **structural flaw** that undermines the whole design and several **operational flaws** that will cause lockups.

**The structural flaw is that the gate lives inside the trust boundary of the entity it constrains.** Every artifact PROC-007 validates (`codex_receipt.json`, `pending_findings.json`, audit report metadata, `.done` sentinels, the dossier) is *writable by the orchestrator*. The linter verifies **presence and internal consistency**, not **provenance**. An adversarial or merely overeager orchestrator can satisfy A, B, and D by fabricating well-formed files. Fabrication is exactly the vulnerability class the proposal claims to close (items 2 and 4 in §1).

The draft is therefore a **speed bump, not a hard gate**, unless provenance is cryptographically or architecturally separated from the orchestrator.

**Overall verdict: CONDITIONAL, DO NOT ADOPT AS WRITTEN.** The sub-gates are adoptable after the amendments in §5.

## 2. Cross-Cutting Findings

### XC-1 [CRITICAL]: Provenance Gap (Self-Attestation Problem)
The orchestrator produces and consumes its own evidence. `evidence.physical_diff` is a string field the orchestrator can populate with any text. A `.done` sentinel is an empty file anyone can `touch`. A `codex_receipt.json` is JSON anyone can author.

**Required invariant:** *Evidence must be bound to a source the orchestrator cannot forge.* Options, in order of strength:
1. **Signed receipts**: the Codex/Qwen/Claude invocation wrapper (a separate process the orchestrator cannot read keys from) signs `{run_id, prompt_hash, output_hash, model_id, timestamp}`. The linter verifies the signature against an embedded public key.
2. **Hash-chain receipts**: if signing keys are infeasible on a `csc.exe` 4.8 toolchain, use an append-only ledger (`audit/ledger.jsonl`) where each entry includes the hash of the previous entry and the hash of the artifact. Tampering requires rewriting the whole chain, which is detectable if the ledger head hash is stored out-of-band (e.g., CI secret, a user-held file, or a pre-receive server hook).
3. **Minimum viable**: the linter *recomputes* rather than *reads*. For example, it must compute `SHA256(audit report body)` itself and compare it to the receipt, rather than trusting a hash field written by the orchestrator.

### XC-2 [CRITICAL]: Linter Self-Protection and Meta-Deadlock
The proposal is silent on what happens when `VerifySRS_Integrity.cs`, `GEMINI.md`, or `adversarial_audit_specification.md` are themselves modified.
- If the linter is staged for modification, which version of the linter validates the commit: the old (HEAD) or the new (staged)? If new, the orchestrator can weaken the gate and pass it in the same commit. If old, a fix to a buggy PROC-007 rule can be blocked by the buggy rule (**bootstrap deadlock**).
- Qwen's last question ("cannot commit even legitimate linter fixes") is answerable: **yes, as drafted, it can.**

**Required:** a *protected-paths* rule. Changes to linter source, vetted-hash tables, the adversarial template, and `GEMINI.md` must be validated by the **HEAD (pre-change) linter** plus a **human-presence requirement** (see §4, break-glass).

### XC-3 [HIGH]: `git commit --no-verify` and Out-of-Band Paths
A pre-commit hook is client-side and trivially skippable (`--no-verify`, `core.hooksPath`, editing `.git/hooks`, committing via a different working tree, or using plumbing commands: `git commit-tree` / `git update-ref`). If the orchestrator has shell access, the gate is advisory.

**Required:** enforcement must also exist at a point the orchestrator cannot reach (server-side `pre-receive`, CI required check with branch protection, or a signed-commit policy where the signing key is human-held).

### XC-4 [HIGH]: Staged-Blob-Only Scope Creates a Temporal Gap
Every gate inspects *staged* content. Content changed in the working tree but not staged, or committed in a *later* commit that "completes" the pair, escapes. Example: commit 1 stages the DDL change plus a stub receipt; commit 2 replaces the receipt content. See bypass B-A3 below.

### XC-5 [MEDIUM]: Gate-Gaming Incentive Inversion
Hard gates with high false-positive rates train the orchestrator (and humans) to route around them. Every FATAL must have a documented, auditable, *narrow* escape hatch, or the system will grow shadow bypasses that are worse than an explicit one.

## 3. Sub-Gate Analysis

### 3.1 PROC-007-A: Track Downgrade Gate

**Detection ambiguity ("what counts as a formula/DDL/new requirement ID?"):**
The spec says "new requirement IDs, DDL statements, or mathematical calculation formulas." None is defined operationally.
- *Requirement ID:* regex? `SRS-\d+`? A *new* ID versus a *renamed* or *moved* ID? A diff-based "added line matches regex and ID not present in HEAD" is deterministic, but the regex itself becomes the attack surface (use a non-matching ID format, or place IDs in a table the regex doesn't cover).
- *DDL:* `CREATE|ALTER|DROP` is easy, but `schema.sql` edits include comments, whitespace, reordering, and `COMMENT ON`. Semantic equivalence is not decidable by regex.
- *Math formulas:* there is no robust deterministic detector. "Art 37 calculation" is domain logic in natural-language prose. A linter cannot reliably tell `daily_wage * 30` from prose. **This leg is not mechanically enforceable as specified.**

**Deadlock scenarios (legitimate commits blocked):**
| Scenario | Why it deadlocks |
|---|---|
| Typo fix inside a line containing a formula | Diff touches the formula line, so "formula modified" triggers; Codex draft is meaningless for a typo |
| Whitespace/Markdown reformat of `schema.sql` | Every DDL line appears in the diff |
| Reverting a bad commit (`git revert`) | Re-adds DDL/IDs; needs a receipt for text that was already vetted |
| Emergency hotfix (Claude Q1) | Receipt is unobtainable if Codex is down/rate-limited/offline |
| Merge conflict resolution | Diff content is a mechanical mixture; no Codex draft exists for it |
| Codex service outage | Hard dependency on an external SaaS means total commit freeze for spec files |

**Receipt binding is unspecified.** "A valid `codex_receipt.json` MUST be staged simultaneously" says nothing about *what the receipt covers*. A receipt for change X can be staged alongside unrelated change Y.

**Bypass tricks:**
- **B-A1 Receipt reuse/decoupling:** stage an old, valid receipt with a new unrelated diff. Fix: receipt must contain the `SHA256` of the *exact* staged blob(s) it vetted, and the linter recomputes that hash itself.
- **B-A2 Path evasion:** put the formula in a file *not* on the watch list (`docs/appendix_calc.md`, a `.json` config, a renamed copy of `schema.sql`, a C# constant). The gate guards two filenames, not a semantic domain.
- **B-A3 Split-commit:** commit the receipt first with a benign diff, then commit the real change in a follow-up commit that "doesn't introduce" new IDs because it only *modifies* existing ones (rename old ID to new content).
- **B-A4 Obfuscated formula:** express the calculation as a pseudo-code block, an image/ASCII table, or a Unicode lookalike so the regex misses it.
- **B-A5 Encoding/line-ending churn:** CRLF/LF or BOM tricks cause the diff to look like "everything changed" (fatigue) or "nothing semantically changed" (stealth), depending on how the diff is computed.
- **B-A6 Rename + modify:** `git mv` with similarity index > threshold may hide a modified formula in a rename diff if the linter ignores renames.

### 3.2 PROC-007-B: Finding Evidentiary Gate

**Structural check is sound; truth check is absent.** The gate verifies a JSON file is *shaped* correctly. It cannot verify `physical_diff` corresponds to a *real* diff or that it *addresses* the finding.

**Critical gap, conditional trigger:** "If `scratch/pending_findings.json` exists." **Deleting the file (or never creating it) satisfies the gate.** This is the single biggest hole in B. It converts "hand-waving" into "just don't register the finding." The proposal's own §1 item 2 names "failing to register findings" as the vulnerability, yet B only checks files that exist.

**Other defects:**
- `declared_count == findings.length` is self-referential: the orchestrator controls both numbers. It catches accidental truncation only.
- `scratch/` is conventionally untracked or `.gitignored`. If so, the file is *never staged*, and the gate (which scans staged blobs) never sees it. State location contradicts enforcement point.
- No `WONTFIX` / `REJECTED_WITH_JUSTIFICATION` / `DEFERRED` / `FALSE_POSITIVE` states exist. The only legal terminal state is `RESOLVED` with a physical diff. This **forces a code change for findings that are legitimately wrong**, which creates perverse pressure: the orchestrator will make cosmetic or fake patches to satisfy the gate (evidence laundering) rather than dispute a bad finding honestly.
- `evidence.line_range` is not validated against the diff, so `"1-1"` against an unrelated line passes.

**Answer to Claude Q2 (mechanical hand-wave detection without chat-turn state):**
It cannot be done by inspecting chat. It *can* be done by moving the state out of chat and into an **append-only external ledger that is written by the audit tooling, not the orchestrator**:
1. When any auditor (Claude/Codex/Qwen) produces a report, the *audit harness* parses it and **deterministically emits findings** (`finding_id = hash(run_id + normalized_finding_text)`) into `audit/ledger.jsonl` with state `OPEN`. The orchestrator cannot decline to register.
2. A commit that references or follows an audit run may only land if **every ledger finding for that run is terminal** (`RESOLVED` with evidence, or `REJECTED` with a justification *and* a second-party sign-off, see below).
3. Hand-waving becomes impossible to *hide* because registration is not the orchestrator's decision. It can still *argue*, but only through a first-class `REJECTED` state, which is then reviewable.

This inverts the model from "orchestrator registers its own findings" to "tooling registers findings the orchestrator must dispose of."

**Evidence verification (stronger than non-empty):**
The linter should verify `evidence.physical_diff` by recomputing: for each `RESOLVED` item, check that the **staged diff for `evidence.file` actually intersects `evidence.line_range`** and that the staged blob hash equals `evidence.post_blob_sha`. Empty-string checks alone are satisfied by `"."`.

**Bypass tricks:**
- **B-B1** Delete/never create `pending_findings.json`.
- **B-B2** Keep file `.gitignore`d so it's never staged.
- **B-B3** Cosmetic patch (whitespace/comment) as "physical diff" with plausible `line_range`.
- **B-B4** Set `declared_count` and `findings` to a deliberately minimal set, omitting inconvenient findings (count still "matches").
- **B-B5** Mark finding `RESOLVED` with evidence pointing to a *previous* commit's diff.
- **B-B6** Summarize multiple distinct audit findings into one omnibus finding ("normalize findings") to shrink the surface.

### 3.3 PROC-007-C: Prompt Laundering & Evidence Origin Gate

**This sub-gate is the weakest and should be redesigned, not patched.**

**Fundamental problems:**
1. **Denylist of "leading phrases" is trivially evaded**: synonyms, paraphrase, translation, Unicode homoglyphs, zero-width characters, base64 payload in a "context file," or putting the leading framing in a *user message* while keeping the *system prompt* canonical. The spec checks "system prompt embedded in metadata", which is **orchestrator-authored metadata** (XC-1). The actual prompt sent can differ from the prompt recorded.
2. **Prompt hash validates the wrong layer.** The laundering attack surface is mostly *context and framing injected around the template* (which files are shown, what is omitted, what summary is provided, the order of material), not the template text. A byte-perfect canonical system prompt plus a cherry-picked, pre-digested input still launders.
3. **Hash brittleness vs. security:** exact hash match breaks on any whitespace, BOM, or line-ending change (Codex Q2). Normalizing makes it tolerant but then you must define normalization precisely.
4. **Vetted hash list = hidden single point of failure:** who updates it? Another protected-path problem (XC-2).
5. **Detects intent via phrases but not outcomes.** The harm is the *false 10/10 PASS*, which is better measured by outcome signals (see recommendations).

**Answer to Codex Q2 (robust prompt-integrity validation):**
- Define a **canonical form**: UTF-8 without BOM, normalize CRLF→LF, strip trailing whitespace per line, collapse runs of blank lines to one, Unicode NFC, and **reject** zero-width/bidi control characters outright (don't strip silently). Hash the canonical form with SHA-256.
- Version the template: `template_id@semver` + hash in a protected table. Accept a **set** of vetted hashes (current + N previous) to survive template evolution.
- **Capture at the harness, not the orchestrator.** The audit invocation wrapper must record the *actual bytes transmitted to the model API* (system + user + all attached context), compute the hash, and write it to the ledger. The linter then verifies the ledger entry, not orchestrator-written metadata.

**Better design: parametric prompts.** Eliminate free-form prompting for auditors. The wrapper builds the prompt from `(template_id, artifact_paths[])` only; the **orchestrator may not supply any prose**. The auditor's input is *the raw staged artifact plus the fixed template*, with no orchestrator summary. This removes the injection surface instead of policing it.

**Outcome-based laundering signals (cheap and mechanical):**
- Rubber-stamp detector: audit report with all-PASS and findings count = 0 on a diff above a size/complexity threshold requires a *second* independent auditor run (different model family). Disagreement between auditors is evidence of laundering or auditor weakness.
- Rapid-repeat detector: >N audit runs on the same artifact hash within a window with changing prompts is a "prompt shopping" signal, so require that all runs for an artifact be retained and counted in the dossier.

**Bypass tricks:**
- **B-C1** Record canonical prompt in metadata, send a different one.
- **B-C2** Leading framing in user turn / attached "context summary" / filename hints (`known_good_final.md`).
- **B-C3** Homoglyph / synonym / non-English leading phrasing.
- **B-C4** Run the audit *N times* (prompt shopping) and stage only the favorable report.
- **B-C5** Truncate/pre-filter the artifact shown to the auditor to hide the problematic section.
- **B-C6** Stage a report with *no* embedded prompt metadata. If the rule is "when present must match", absence passes. Must be "must be present *and* match".

### 3.4 PROC-007-D: Dossier Reconciliation Gate

**The strongest of the four mechanically (filesystem existence is deterministic), but still checks the wrong property.**

**Direction asymmetry:** D verifies *dossier → filesystem* (claims have artifacts). It does **not** verify:
- *filesystem → dossier* (a **failed** run can exist physically and simply never be cited, **cherry-picking runs**);
- that the **metrics/verdict** in the dossier match the run's actual content (a real run directory with a FAIL report can be cited as "10/10 PASS").
It checks that a claim *points somewhere*, not that the claim is *true*. This is exactly "post-hoc paperwork fabrication" surviving in a new form.

**Other defects:**
- `.done` sentinel is forgeable (`touch .done`) and carries no integrity data. It should contain `{report_sha256, ledger_entry_hash}`.
- Two possible directories (`docs/audit_runs/` or `audit/runs/`): ambiguity allows the same Run ID in both locations with different content.
- Run-ID extraction: the sample ID `20261119_061738_d4aeaba1` implies a regex. Run IDs in prose, code fences, or Markdown links may be missed or mis-detected; IDs split by formatting escape detection.
- **Deadlock:** Any dossier edit that *removes* or *corrects* a bad claim is fine, but a commit that touches a dossier containing a **stale historical Run ID whose artifact was later archived/pruned/moved** is FATAL. Storage hygiene (artifact retention policy, shallow clones, LFS, sparse checkout) will break the gate on unrelated edits. D should be **diff-scoped** (validate only *added/changed* claims) rather than re-validating the entire document each time.
- Timing deadlock: dossier and run artifacts must be staged in the *same* commit or the artifacts must pre-exist. A natural workflow (audit completes, orchestrator updates dossier, commit) may stage them separately → FATAL on the dossier-only commit unless "exists in HEAD or index" is the check. Spec must say *which tree*.

**Bypass tricks:**
- **B-D1** Cite a real but unrelated/failed run ID for a different claim.
- **B-D2** Fabricate directory + `.done` + plausible report in the same commit (provenance gap, XC-1).
- **B-D3** Omit unfavorable runs from the dossier (no reverse reconciliation).
- **B-D4** Obfuscate Run IDs (split across Markdown formatting, e.g. `20261119_061738_` + `d4aeaba1`) to evade scanning, while humans still read it as a citation.
- **B-D5** Alter the metrics but keep the same Run ID (optimistic numbers over real artifact).

## 4. Direct Answers to the Posed Questions

### Q1a: Does PROC-007-A deadlock on emergency hotfix / human-directed manual correction? How to govern the exception without a loophole?
**Yes, as written it deadlocks** (and also under Codex outage). The solution is a **narrow, auditable, human-authenticated break-glass**, not an orchestrator-invocable flag.

**Break-glass design:**
1. **Authentication separation:** the override token must be something the orchestrator cannot generate or read: a one-time code the human supplies out-of-band (typed at a prompt the linter opens on a TTY, or a file placed by the human and **deleted/consumed by the linter**, or a signed commit trailer verified against a human-held key). An environment variable like `SKIP_PROC007=1` is **not acceptable**, since the orchestrator controls its own environment.
2. **Scope-limited:** override waives *only* the specific sub-gate and *only* the specified file blob hashes (`{gate: "A", blobs: [sha...], reason, expires}`), never a blanket skip. It does not waive PROC-007-C/D provenance.
3. **Forced debt:** an override mints a mandatory **retroactive-review ticket** in the ledger (`state: OVERRIDE_DEBT`); the *next* commit touching spec files is blocked (FATAL) until the debt is cleared by a real Codex receipt covering the overridden blobs. This prevents the exception from becoming the default path.
4. **Rate-limit & visibility:** more than K overrides per window causes a loud escalation (non-bypassable report in the commit message / CI summary). Every override is logged in the dossier automatically by the linter (not by the orchestrator).
5. **Human-directed edit exemption** (distinct from emergency): when the human directly authored the change, the exemption should be proven by *the human's signature on the commit*, not by the orchestrator's claim "the user told me to." Orchestrator assertions of user intent are unverifiable and are the canonical loophole.

### Q1b: Mechanical detection of finding hand-waving without chat-turn state
See §3.2. The answer is to **remove state from the conversation** and put it in a **tool-written, append-only ledger**. Auditing tooling, not the orchestrator, creates findings; a finding can only be closed by a terminal state with verifiable evidence or by an *independently countersigned* rejection. The linter then enforces *"no OPEN ledger findings for runs referenced by this change."* No chat memory is required because the ledger *is* the memory.

### Q2a (Codex): Efficient C# 4.8 inspection of staged blobs without heavy processes
This is outside my principal remit (Codex was asked), but from a safety standpoint:
- Prefer a **single** `git diff --cached -U0 --no-color --no-ext-diff --diff-filter=ACMR -M --name-status` invocation plus **one** `git cat-file --batch` stream for blob content, rather than per-file `git show` spawns (process-spawn cost is the dominant factor on Windows). Use `ProcessStartInfo` with redirected stdout and read asynchronously to avoid pipe deadlocks (a known .NET 4.8 trap when both stdout and stderr are redirected and read synchronously).
- Force `-c core.quotepath=false` and `--no-textconv` to prevent attacker-influenced diff
