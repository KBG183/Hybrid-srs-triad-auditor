### Interaction Matrix & Adversarial Simulation Narrative

**1. Rule Extraction & State Analysis**
The specification defines a multi-tenant store management system with strict concurrency controls (MySQL `FOR UPDATE NOWAIT` / `FOR SHARE NOWAIT`) and a specific state machine for staff employment (`PENDING` -> `ACTIVE` -> `RESIGNED`). Key legal/operational constraints include:
*   **Wage Integrity:** `hourly_wage` is immutable after initial contract creation unless a new contract is scheduled.
*   **Concurrency:** Lock acquisition order is Member -> Store -> Staff -> Contract. Failure results in 503 `STORE_RETRY_LATER`.
*   **Contract Continuity:** Contracts must form a continuous timeline. Inserting a contract before an existing `SCHEDULED` contract is forbidden (409 `CONTRACT_ORDER_VIOLATION`).
*   **Resignation Logic:** Resignation cancels future contracts and sets the `effective_to` of the current contract to `resigned_date + 1`.

**2. Adversarial Simulation: The "Mid-Shift Resignation" & Wage Gap Paradox**

*Scenario:*
1.  **State:** Staff Member A is `ACTIVE` at Store X. Current contract: `effective_from: 2026-11-01`, `effective_to: NULL`, `hourly_wage: 1500 JPY`.
2.  **Event:** On **2026-11-15**, the Owner initiates resignation for Member A with `resignedDate: 2026-11-15`.
3.  **System Action (REQ-STORE-003):**
    *   Sets `store_staff.employment_status` to `RESIGNED`.
    *   Sets `store_staff.resigned_date` to `2026-11-15`.
    *   Updates the current contract row: `effective_to` becomes `2026-11-16` (resigned_date + 1).
    *   *Crucially:* The specification states: *"Staff is... limited to... `employment_status=ACTIVE`"* for normal business operations (REQ-STORE-004).
    *   *Crucially:* The specification states: *"Staff... can read... labor condition notice... for `joined_date <= asOf <= resigned_date`"* (REQ-STORE-003 Output).

*The Conflict:*
The system immediately flips `employment_status` to `RESIGNED` upon the resignation API call. However, the physical reality of labor is that the employee works *through* the day of resignation.
*   **Time 09:00:** Employee clocks in. System checks `employment_status`. It is `RESIGNED`.
*   **Result:** The system denies clock-in or marks the work as invalid/unrecorded because the "normal business" scope requires `ACTIVE` status.
*   **Legal/Operational Harm:** The employee has worked 8 hours on their final day. The system has no mechanism to record this work because the `ACTIVE` flag was revoked at the *start* of the resignation process (or the moment the API was called), not at the *end* of the workday.
*   **Wage Calculation Gap:** Section 4 states Slice 1 hands off "unique contract history ID... to subsequent processing." If the clock-in system rejects the punch due to `RESIGNED` status, no work record exists. If the clock-in system *allows* the punch (ignoring status), it violates REQ-STORE-004's scope definition for "normal business." If it allows it but the wage calculation engine only looks at `ACTIVE` periods, the wages are lost.

**3. Adversarial Simulation: The "Contract Insertion Deadlock" vs. "Resignation Race"**

*Scenario:*
1.  **State:** Contract A (`2026-11-01` to `NULL`).
2.  **Thread 1 (Owner):** Attempts to add Contract B (`2026-12-01` to `NULL`).
3.  **Thread 2 (Owner):** Attempts to Resign Staff on `2026-11-15`.
4.  **Lock Order:** Both acquire `store_staff` lock.
5.  **Race Condition:**
    *   Thread 1 succeeds: Contract A `effective_to` becomes `2026-12-01`. Contract B created.
    *   Thread 2 (Resignation) proceeds. It looks for "contracts starting after resigned_date (2026-11-15)".
    *   It finds Contract B (`2026-12-01`). It cancels Contract B.
    *   It sets Contract A `effective_to` to `2026-11-16`.
    *   **Result:** The staff is resigned. The future contract is cancelled.
    *   **The Flaw:** What if Thread 2 (Resignation) acquires the lock *first*?
        *   Thread 2 sets `employment_status` to `RESIGNED`.
        *   Thread 1 (Add Contract) attempts to run. REQ-STORE-003 states: *"Contract addition targets `ACTIVE` membership."*
        *   Since Thread 2 already committed `RESIGNED`, Thread 1 fails with 404 or 409.
        *   *This is safe.*

    *   **However, consider the "Same Day" Resignation Edge Case:**
        *   Resignation Date: `2026-11-15`.
        *   Current Date: `2026-11-15`.
        *   Spec: *"Resignation date... must be Japanese business day... prior to or including today."*
        *   Spec: *"Resignation... cancels all unapplied reservations starting after resignation date."*
        *   Spec: *"Sets `effective_to` of final valid contract to resignation date + 1."*
        *   **Ambiguity:** Does "final valid contract" include the one being modified? Yes.
        *   **Ambiguity:** What if there is a `SCHEDULED` contract starting *today* (`2026-11-15`)?
            *   Spec: *"Resignation date... prior to or including today."*
            *   Spec: *"Cancels... reservations starting after resignation date."*
            *   If a contract starts *on* the resignation date, it is NOT cancelled (since it doesn't start *after*).
            *   But the resignation sets the *previous* contract's end to `resigned_date + 1`.
            *   If the "previous" contract was the one starting today, its `effective_to` is set to `2026-11-16`.
            *   This creates a 1-day contract.
            *   **Legal Risk:** If the employee worked 1 hour, they are entitled to wages. If the system treats `RESIGNED` status as "no access to clock in," the 1 hour is unrecorded.

**4. Adversarial Simulation: The "Ghost Work" via 503 Retry Failure**

*Scenario:*
1.  Employee attempts to clock in.
2.  System hits a lock timeout (503 `STORE_RETRY_LATER`).
3.  Client retries.
4.  Between retry 1 and retry 2, the Store Owner rotates the Invite Code (REQ-STORE-001).
5.  The clock-in endpoint (implied in Section 4 "Handover to Attendance") likely relies on the Store's existence and validity.
6.  If the clock-in logic depends on the `store_staff` row being `ACTIVE`, and the resignation happened in the interim, the retry fails with 404.
7.  **Result:** The employee physically worked, but the system has no record because the state changed between the physical act and the successful API commit. The "Silent Default" of 503 retries assumes state stability which is not guaranteed in a high-churn environment.

**5. Adjudication of Findings**

*   **P1 Blocked-Terminator (Wage Loss):** The transition to `RESIGNED` status immediately upon API call, combined with the requirement for `ACTIVE` status for "normal business" (clock-in), creates a window where work performed on the resignation day cannot be recorded if the API call precedes the work.
*   **P2 Record-vs-Reality Divergence:** The `effective_to` boundary logic (`resigned_date + 1`) assumes the contract covers the entire resignation day. If the employee leaves at 10:00 AM, the system still marks the contract as valid until 23:59:59 of that day. If they are re-hired the next day, the contract continuity might be broken or require complex merging, but more importantly, the *wage calculation* for the partial day relies on "actual work time" which is not captured in Slice 1's schema (no `clock_in` table in Slice 1, but Slice 1 *hands off* to it). The handoff contract is fragile.
*   **P4 Rule Collision:** REQ-STORE-003 states "Resignation... cancels all unapplied reservations starting *after* resignation date." It does *not* cancel reservations starting *on* the resignation date. However, it sets the `effective_to` of the *current* contract to `resigned_date + 1`. If the "current" contract *is* the one starting on the resignation date (a same-day start), its `effective_to` is set to `resigned_date + 1`. This is logically consistent but operationally dangerous for wage proration if the "actual work" system doesn't handle the `RESIGNED` status override for the final day.
