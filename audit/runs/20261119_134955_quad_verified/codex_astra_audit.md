# KINTAI SRS v1.0.2 アーキテクチャ・並行性監査報告書

**総合判定は FAIL です。** 提示された仕様どおりに実装すると、同一人物の複数店舗でのシフト重複確定を防げず、給与計算では同じ勤務実績から異なる確定額を導けます。また、MySQL 8.4 で実行できない SQL が必須処理に含まれています。この3点は実装着手前に正本で解消する必要があります。

監査対象は、ご提示の `config/srs_specification_ssot.md` 相当の日本語本文12要件です。正本の直接読み取りとリポジトリ列挙は実行ポリシーにより `rejected: blocked by policy` となりました。このため、以下は**仕様の静的監査結果**です。実ファイルとの同一性、ドメインサービス・Mapper・DDLとの対応、MySQL実機試験、C#リンターの結果は未検証です。指定のQwen監査は設定・ランナーを確認できず未実行で、接続失敗の判定も行っていません。

## 1. MySQL 8.4 の制約と並行性

| Finding ID | 判定 | 対象要件 | 技術所見・是正条件 |
|---|---|---|---|
| DB-01 | **FAIL** | STORE-001、MEMBER-001、SHIFT-004 | 未退勤行の `CREATE UNIQUE INDEX ... WHERE`、登録時の `ON CONFLICT`、日時型 `TIMESTAMPTZ` がMySQL向け必須経路に混在しています。未退勤制約は、未退勤時のみ `store_staff_id` を返し、退勤済みなら `NULL` を返す生成列に `UNIQUE` を設定すれば表現できます。メールの関数索引はMySQL構文 `((LOWER(email)))` と照合順序を明示し、通常の `INSERT` で対象キーの重複エラー1062を409に対応付けます。招待コードの再生成も対象キーの1062に限定します。カレンダーは保存時刻の基準と東京時間から検索境界への変換を定義してください。[MySQL 8.4 CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) |

| LOCK-02 | **FAIL** | SHIFT-001/002、STAFF-002 | `REPEATABLE READ` では、先行する通常の `SELECT` が作ったスナップショットを、ロック取得後の通常の重複照会でも参照し得ます。親行待機中に相手が確定したシフトや契約を見落とす経路が残ります。全更新経路で同じ親行をロックし、重複対象の照会自体を最新状態のロッキングリードとする必要があります。外側の照会に付けた `FOR UPDATE` がサブクエリにも及ぶという前提は置けません。[MySQL 8.4 Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)・[Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) |

| LOCK-04 | **FAIL** | LABOR-001/004、STAFF-002 | 精算側が店舗行をロックしても、全打刻・休憩訂正・契約変更が同じロック規約に参加する保証はありません。さらに店舗Aのロックだけでは、店舗Bでの遡及訂正による同一人物の日・週累計の変化を防げません。精算対象期間を締め日から導出し、集計に使用する他店舗実績の版、取得順序、締め後訂正の帰属先を定義してください。確定明細には入力版と適用単価を保存し、同一入力版から金額を再現できることを受入条件とします。 |

## 2. 給与算定と端数処理

## 3. ドメインサービスとの双方向トレーサビリティ

**TRACE-01 — FAIL（提示文書の追跡性）**。12要件には識別子とDoDがありますが、実装シンボル、MyBatis statement ID、マイグレーション、試験ID、実行証跡への対応がありません。特に、打刻・休憩訂正は給与確定の整合性を左右する一方、提示本文にはSlice 3の要件がありません。以下は対応を確認すべき責務です。実在するクラス名は未確認です。

## 4. 再監査の受入条件

| 試験 | 操作 | 合格条件 |
|---|---|---|
| AT-01 | MySQL 8.4の空スキーマへ全DDLを適用し、同一所属の未退勤2件、退勤済み複数件、大文字小文字のみ異なるメールを登録 | DDLが完走し、未退勤の2件目と重複メールだけが対象制約で拒否されます。 |
| AT-02 | 独立した2接続で同一人物・異店舗・重複時間帯を同時確定。片方が事前に通常読取りを済ませた条件でも実行 | 確定は1件です。ロック競合後の再試行でも先行確定を認識し、店舗詳細を開示しません。 |
| AT-03 | 初回精算で、先行トランザクションが店舗ロックを保持している場合とコミット済みの場合を別々に実行 | 保持中は採用した待機方針どおりに応答し、確定済みは409になります。ヘッダー・明細ともに1回分だけが残ります。 |
| AT-04 | 同一の割増対象6秒を「連続6秒」と「1秒×6」に分割して月次確定。日・週・月の超過境界も前後1秒で比較 | 両入力の25%割増確定額はともに1円です。各閾値を超えた秒だけに新しい率が適用されます。 |
| AT-05 | 異店舗の遡及訂正と月次確定を並行実行し、保存した入力版から明細を再計算 | 各明細を同一金額で再現できます。訂正は規定の精算期間に一度だけ反映されます。 |

**是正の優先順位は、人物単位の共通ロック、給与の整数分子契約、MySQL方言・競合応答の一本化です。** この3点を正本に反映し、実際のサービスからMapper・DDL・試験結果まで双方向にたどれる証跡がそろった時点で、実装適合性を再判定できます。
