*   **Event E2 (Work Execution):** Staff clocks in/out on Day `D`.

**3. Interaction Matrix (Guard vs. Event)**
*   **Guard:** `employment_status = 'ACTIVE'` required for "Normal Business" (Clock-in/Out).
*   **Conflict:** On Day `D` (Resignation Day), the status is `RESIGNED`.
    *   If the system strictly enforces `ACTIVE` for clock-in *after* the resignation transaction commits, the staff member cannot record work for Day `D` if they resign during the day or if the system state flips before the end of the day.
    *   However, the spec implies resignation is a discrete event. The critical gap is in **Wage Calculation** and **Record Validity**.

**4. Adversarial Simulation**
*   **Scenario 1: The "Ghost" Resignation Wage Gap (P0)**
    *   **Time:** 2026-11-23 09:00 JST.
    *   **Action:** Owner processes resignation for Staff A with `resignedDate = 2026-11-23`.
    *   **DB State:** `store_staff.employment_status = 'RESIGNED'`. `contract_history.effective_to = 2026-11-24`.
    *   **Action:** Staff A works a full shift on 2026-11-23 (09:00 - 18:00).
    *   **System Check:** The wage calculation engine (Slice 2/3) queries `store_staff` for Staff A on 2026-11-23.
    *   **Logic Flaw:** The spec `[REQ-STORE-004]` restricts "Normal Business" to `ACTIVE` status. If the clock-in system checks status *at the time of clock-in* (which is standard for real-time validation), Staff A *can* clock in if the resignation happens *after* clock-in. But if the resignation happens *before* the shift ends, does the system allow the clock-out?
    *   **Critical Gap:** The spec `[Section 4]` says Slice 1 hands over the "Contract History ID". It does **not** specify that the `RESIGNED` status must be ignored for wage calculation on `resigned_date`. In fact, `[REQ-STORE-003]` says "Staff... can read-only query... labor condition notices... `joined_date ≤ asOf ≤ resigned_date`". This implies the *contract* is valid. But does the *employment relationship* allow the *recording* of work?
    *   **The Paradox:** If `employment_status` is `RESIGNED`, `[REQ-STORE-004]` says staff access is limited to `ACTIVE`. If Staff A tries to clock out *after* the resignation is processed (e.g., resigns at 12:00, works until 18:00), the system might reject the clock-out or mark the record as invalid because the status is no longer `ACTIVE`. The spec **fails to decouple** the `RESIGNED` status from the validity of work performed *on* the resignation date. It treats `RESIGNED` as a terminal state for *all* operations, including those occurring on the final day of employment.

*   **Scenario 2: Retry Idempotency Failure (P1)**

If the first request *succeeded* but the client didn't get the response, the retry hits the `ACTIVE` state and returns 200. This is safe.
    *   **However**, consider the `PENDING` to `ACTIVE` transition. If the first request is in-flight (holding lock) and the second request arrives, it gets 503 (Lock Conflict). The client retries. This is handled.
