# SRS 技術実装完全性監査レポート (L2 Integrity Audit Report)

監査対象は提供された `kintai_master_srs.md` 本文です。実リポジトリコード、実行テスト、およびリモートQwen 27B監査ログとの照合前に実施された、ドキュメント自体の整合性および実装可能性に関する静的監査結果です。

総合判定: **FAIL**  
主な要因は、給与帳簿の不変性、複数店舗外部キーの完全性、契約履歴の重複防止、並行性制御に関する実行可能な詳細契約の不足によるものです。

| Finding ID | 点検項目 | 重要度 (P0/P1/P2) | 判定 (FAIL/WARN) | 根拠 (文書位置/内容) | 技術分析および改善勧告 |
|---|---|---:|---|---|---|
| F-001 | 給与確定帳簿の不変性 | P0 | FAIL | 第2章 `payroll_daily_detail`; 第6章 給与確定 | `payroll_daily_detail` の `attendance_id` が複数の `payroll_id` に再利用可能であり、同一勤怠が複数給与に重複計上されるリスク。`UNIQUE(attendance_id)` または清算所有権テーブルを追加し、確定後の元勤怠・契約変更を遮断するDB/サービス規約を明記する必要がある。 |
| F-002 | 給与確定者カラムの不整合 | P0 | FAIL | 第2章 `payroll` DDLに `confirmed_by` なし; 第6章では `confirmed_by=reviewerId` 保存と記述 | API要件をDBに永続化不能。`confirmed_by BIGINT` 外部キーおよび確定履歴テーブルを追加するか、仕様記述を是正する必要がある。 |
| F-003 | 複数店舗複合外部キーの不完全性 | P0 | FAIL | `attendance.shift_id → shift_schedule.shift_id`, `attendance` の `store_id/store_staff_id` 分離 | `attendance.shift_id` のみでは、紐付くシフトが同一スタッフ・同一店舗であることをDBレベルで保証不能。`FOREIGN KEY (shift_id, store_id, store_staff_id)` 構造またはサービス内の強制検証と結合テストが不可欠。 |
| F-004 | 契約履歴期間の重複 | P0 | FAIL | `store_staff_contract_history`; `UNIQUE(store_staff_id,effective_from)` | 異なる `effective_from` を持つ契約期間が重複する可能性。サービス検証のみでは同時リクエストを防御不能。スタッフ別契約行ロック後の検証・更新、またはPostgreSQL exclusion constraintに準ずるMySQLトリガー/検証テーブル戦略を明記する必要がある。 |
| F-005 | 並行性制御が擬似コード水準 | P0 | FAIL | 第1章 1.3, 第4章 4.3, 第5章 5.4, 第6章 6.3 | `SELECT ... FOR UPDATE` の言及はあるが、実際のロック対象、順序、トランザクション境界、分離レベル、デッドロック再試行ポリシーが欠落。Mapper SQLとトランザクション順序を明記し、同時打刻・修正承認・給与確定の競合テストを追加する必要がある。 |
| F-006 | マルチインスタンス並行性 | P1 | WARN | 第1章では悲観的ロックのみ提示 | DB行ロックは同一DBを共有する場合にのみ有効。複数アプリインスタンス運用を想定する場合は分散ロックまたはDB単一ライター方針を選択し、想定しない場合は単一インスタンス制約を明記する必要がある。 |
| F-007 | アクティブ勤怠重複防止のDB保護不足 | P0 | FAIL | 第5章 5.4 `CLOCK_IN` 重複検証 | アプリケーションの参照後INSERT方式では同時リクエストで重複行が生成されるリスク。アクティブ勤怠を別状態テーブルに分離するか、スタッフ・勤務日基準の単一打刻行と条件付き更新を採用し、DBレベルのユニーク戦略を追加する必要がある。 |
| F-008 | APIエラー契約の不一致 | P1 | FAIL | 第1章 1.4と各APIの `IllegalArgumentException`, `409 Conflict` 記述 | 例外型とHTTPステータスマッピング、エラーコード、フィールドエラーschemaが未確定。`errorCode`, `message`, `fieldErrors`, `traceId` 形式を固定し、例外別マッピング表を作成する必要がある。 |
| F-009 | リクエストDTOの認証主体混用 | P1 | FAIL | シフト申請は `storeId`, `storeStaffId` 受信; 第1章では認証情報信頼を要求 | DTOでIDを受け取ることと、認証主体をサーバー側で決定する規則が混在。STAFFリクエストでは `storeStaffId` を除去するか認証会員から再取得し、OWNERの対象スタッフアクセス検証規則をAPI毎に明記する必要がある。 |
| F-010 | DTO検証ルールの欠落 | P1 | FAIL | 第3~6章 Request JSON 仕様 | 必須/任意/null許容、文字列長、enum、時間形式、負数金額、理由文字数、`requestedEndTime == startTime` 等の適用有無が不明確。Bean Validation アノテーションとエラー応答例をDTO毎に確定する必要がある。 |
| F-011 | シフト重複・重複期間の無欠性未保証 | P1 | WARN | 第4章 時間重複検査 | 同一スタッフの重複シフトをサービス層のみで検査しておりDB制約が存在しない。同時提出時の迂回を防ぐため、スタッフ・期間ロック後の重複検査または予約テーブル/検証トランザクションを明記する必要がある。 |
| F-012 | 給与計算ポリシーの内部矛盾 | P1 | FAIL | 第6章 6.3: 「警告のみ表示」と「清算実行中断」が併記 | `PENDING` 修正申請や `MOD_REQUESTED` 勤怠が存在する際、計算を中断するのか警告後続行するのかが矛盾。基本方針を一つに決定し、APIステータスコードとメッセージを固定する必要がある。 |
| F-013 | 日別残業時間計算境界の曖昧さ | P1 | WARN | 第5章 計算機と第6章 日別合算規則 | 勤怠毎に `overtimeMinutes` を算出した後に合算すると、同一日付の複数勤怠で8時間基準が二重適用されるリスク。日付別勤務分を先に合算した後に超過分を算出する単一アルゴリズムに統一し、テストする必要がある。 |
| F-014 | 給与期間中の契約上限処理不足 | P1 | WARN | 第6章 契約別月間交通費上限 | 期間中に上限が変更された場合「中断する」とあるのみで、既存ドラフト給与の削除・再計算・状態復旧手順が未定義。契約期間別上限検証、計算失敗時の原子的ロールバック、管理者対応手順を定義する必要がある。 |
| F-015 | 勤怠修正と給与確定の日付範囲検証不足 | P0 | FAIL | 第5章 5.4, 第6章 6.3 | 勤怠の `work_date` のみを検証すると、修正された出退勤時刻が別の日付・別の清算期間へ移動するケースを見落とすリスク。修正前後の両日付と両給与期間を計算して確定状態を検証する必要がある。 |
| F-016 | スキーマ状態値制約の不足 | P1 | WARN | `member.role`, `employment_status`, `clock_in_method` DDL | 一部カラムにコメントのみで `CHECK` 制約がない。`ROLE_OWNER/ROLE_STAFF`、在籍状態、打刻方式、日付・状態の組み合わせをDB制約または厳格なenum検証で強化する必要がある。 |
| F-017 | シフト・勤怠時間範囲のDB検証不足 | P1 | FAIL | `shift_schedule`, `attendance` DDL | 終了時刻が開始時刻より後か、最大16時間以内か、休憩が全体範囲内か等のDDL制約が欠落。サービス検証のみでは手動SQL・競合リクエストを防げないため、原子的サービス検証と完全性テストが必要。 |
| F-018 | 削除・変更履歴ポリシー未定義 | P1 | WARN | 全体的な監査証跡要件 | `ON DELETE` ポリシーがなく、元勤怠・契約・シフトの削除可否も未定義。監査対象テーブルは削除禁止または論理削除とし、給与確定データは append-only ポリシーを明記する必要がある。 |
| F-019 | インデックスの業務参照パターン不適合 | P2 | WARN | 第2章 DDL および 勤怠・給与API | `attendance_mod_request(store_id, approval_status, work_date)`、給与状態・期間照会、契約有効期間単一照会用の複合インデックスが未定義。実クエリ別実行計画検証とインデックス基準を追加する必要がある。 |
| F-020 | タイムゾーン・現在日基準の実行契約不足 | P1 | WARN | 第1章 `Asia/Tokyo` 原則; 各サービスの `LocalDate.now()` | アプリケーションJVM、DBセッション、コネクションプールのタイムゾーンが一致する設定とテストが欠落。`Clock` 注入、`ZoneId.of("Asia/Tokyo")` 使用、日付跨ぎ結合テストを明記する必要がある。 |
| F-021 | スキーマ初期化・マイグレーション戦略未完成 | P1 | FAIL | 第1章・第2章 `CREATE TABLE IF NOT EXISTS` 注意事項 | 既存テーブルを変更できないDDLである一方、バージョン管理されたマイグレーションツールや実行順序が欠落。Flyway等の導入または明確な開発DB再生成手順を策定する必要がある。 |
| F-022 | セキュリティ境界が要件水準に留まる | P0 | FAIL | 第1章 1.2.1, 1.3 | メニュー非表示はセキュリティ境界ではないと明記された一方、API別OWNER/STAFF所属検証マトリクス、CSRFポリシー、IDORテストが不足。エンドポイント別権限・所有権検証表と統合セキュリティテストを追加する必要がある。 |
| F-023 | 給与確定API再検証契約の不完全性 | P0 | FAIL | 第6章 `expectedGrossPay`, `expectedTotalPay` | 2つのリクエストフィールドが同義であり、`changedDiff` の構造も未定義。単一の `expectedGrossPay` に統一するか総額・内訳別の期待値を明確にし、不一致時のエラーschemaを定義する必要がある。 |
| F-024 | 監査証跡要件の欠如 | P1 | WARN | 全体DoDおよび承認履歴要件 | 誰がいつどのリクエスト・SQL・計算バージョンを使用したかを保持する実行証跡schemaがない。承認・確定・再計算イベントに actor, timestamp, before/after hash, rule version を記録する必要がある。 |
