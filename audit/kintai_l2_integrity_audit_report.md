# SRS 기술 구현 무결성 감사 결과

감사 범위는 제공된 `kintai_master_srs.md` 본문입니다. 실제 저장소 코드·실행 테스트·원격 Qwen 27B 감사 로그는 현재 확인되지 않았으므로, 아래 결과는 문서 자체의 정합성 및 구현 가능성에 대한 정적 감사입니다.

종합 판정: **FAIL**  
주요 원인은 급여 장부 불변성, 다점포 외래키 무결성, 계약 이력 중복 방지, 동시성 제어의 실행 가능한 세부 계약이 부족하기 때문입니다.

| Finding ID | 점검 항목 | 심각도 (P0/P1/P2) | 판정 (FAIL/WARN) | 근거 (문서 위치/내용) | 기술 분석 및 개선 권고안 |
|---|---|---:|---|---|---|
| F-001 | 급여 확정 장부 불변성 | P0 | FAIL | 제2장 `payroll_daily_detail`; 제6장 급여 확정 | `payroll_daily_detail`의 `attendance_id`가 여러 `payroll_id`에 재사용될 수 있어 동일 근태가 여러 급여에 중복 포함될 수 있습니다. `UNIQUE(attendance_id)` 또는 정산 소유권 테이블을 추가하고, 확정 이후 원본 근태·계약 변경을 차단하는 DB/서비스 규칙을 명시해야 합니다. |
| F-002 | 급여 확정자 컬럼 불일치 | P0 | FAIL | 제2장 `payroll` DDL에는 `confirmed_by` 없음; 제6장에서는 `confirmed_by=reviewerId` 저장 | API 요구사항을 DB가 저장할 수 없습니다. `confirmed_by BIGINT` 외래키와 확정 이력 테이블을 추가하거나 문서의 저장 요구를 제거해야 합니다. |
| F-003 | 다점포 복합 외래키 불완전 | P0 | FAIL | `attendance.shift_id → shift_schedule.shift_id`, `attendance`의 `store_id/store_staff_id` 분리 | `attendance.shift_id`만으로는 연결된 시프트가 동일 직원·동일 매장인지 DB가 보장하지 않습니다. `FOREIGN KEY (shift_id, store_id, store_staff_id)` 구조 또는 서비스 내 강제 검증과 통합 테스트가 필요합니다. |
| F-004 | 계약 이력 기간 겹침 | P0 | FAIL | `store_staff_contract_history`; `UNIQUE(store_staff_id,effective_from)` | 서로 다른 `effective_from`을 가진 계약 기간이 겹칠 수 있습니다. 서비스 검증만으로는 동시 요청을 막을 수 없습니다. 직원별 계약 행 잠금 후 검증·갱신하고, PostgreSQL exclusion constraint에 준하는 MySQL 트리거/검증 테이블 전략을 명시해야 합니다. |
| F-005 | 동시성 제어가 의사코드 수준 | P0 | FAIL | 제1장 1.3, 제4장 4.3, 제5장 5.4, 제6장 6.3 | `SELECT ... FOR UPDATE`가 언급되지만 실제 잠금 대상, 잠금 순서, 트랜잭션 경계, 격리수준, 데드락 재시도 정책이 없습니다. Mapper SQL과 트랜잭션 순서를 명시하고, 동시 출근·수정 승인·급여 확정 경합 테스트를 추가해야 합니다. |
| F-006 | 다중 인스턴스 동시성 | P1 | WARN | 제1장에서는 비관적 락만 제시 | DB 행 잠금은 동일 DB를 공유할 때만 유효합니다. 다중 애플리케이션 인스턴스 운영을 고려한다면 분산 락 또는 DB 기반 단일 writer 정책을 선택하고, 선택하지 않는다면 단일 인스턴스 제한을 명시해야 합니다. |
| F-007 | 활성 근태 중복 방지 DB 보호 부족 | P0 | FAIL | 제5장 5.4 `CLOCK_IN` 중복 검증 | 애플리케이션 조회 후 INSERT 방식은 동시 요청에서 중복 행을 만들 수 있습니다. 활성 근태를 별도 상태 테이블로 분리하거나, 직원·근무일 기준 단일 타각 행과 조건부 갱신을 사용하고 DB 수준의 유일성 전략을 추가해야 합니다. |
| F-008 | API 오류 계약 불일치 | P1 | FAIL | 제1장 1.4와 각 API의 `IllegalArgumentException`, `409 Conflict` 서술 | 예외 타입과 HTTP 상태 매핑, 오류 코드, 필드 오류 schema가 확정되어 있지 않습니다. `errorCode`, `message`, `fieldErrors`, `traceId` 형식을 고정하고 예외별 상태 매핑표를 작성해야 합니다. |
| F-009 | 요청 DTO의 인증 주체 혼용 | P1 | FAIL | 시프트 요청은 `storeId`, `storeStaffId` 수신; 제1장에서는 인증 정보 신뢰 요구 | DTO에 ID를 받는 것과 인증 주체를 서버에서 결정하는 규칙이 혼재합니다. STAFF 요청에서는 `storeStaffId`를 제거하거나 서버에서 인증 회원으로 재조회하고, OWNER의 대상 직원 접근 검증 규칙을 API별로 명시해야 합니다. |
| F-010 | DTO 검증 규칙 누락 | P1 | FAIL | 제3~6장 Request JSON 명세 | 필수/선택/null 허용, 문자열 길이, enum, 시간 형식, 음수 금액, 사유 길이, `requestedEndTime == startTime`의 모든 API 적용 여부가 불명확합니다. Bean Validation 어노테이션과 오류 응답 예시를 DTO별로 확정해야 합니다. |
| F-011 | 시프트 중복·겹침 무결성 미보장 | P1 | WARN | 제4장 시간 겹침 검사 | 동일 직원의 겹치는 시프트를 서비스에서만 검사하며 DB 제약이 없습니다. 동시 제출 시 우회될 수 있으므로 직원·기간 잠금 후 겹침 검사 또는 예약 테이블/검증 트랜잭션을 명시해야 합니다. |
| F-012 | 급여 계산 정책 내부 모순 | P1 | FAIL | 제6장 6.3: “단순 경고만 표시”와 “정산 실행 중단”이 함께 존재 | `PENDING` 수정 요청·`MOD_REQUESTED` 근태가 있을 때 계산을 중단하는지 경고 후 진행하는지 충돌합니다. 기본 정책을 하나로 결정하고, API 상태 코드와 사용자 메시지를 고정해야 합니다. |
| F-013 | 일별 초과근로 계산 경계 모호 | P1 | WARN | 제5장 계산기와 제6장 일별 합산 규칙 | 근태별로 `overtimeMinutes`를 계산한 뒤 합산하면 동일 날짜 여러 근태의 8시간 기준이 중복 적용될 수 있습니다. 날짜별 근무분을 먼저 합산한 뒤 초과분을 계산하는 단일 알고리즘으로 통일하고 테스트해야 합니다. |
| F-014 | 급여 기간 중 계약 상한 처리 불충분 | P1 | WARN | 제6장 계약별 월 교통수당 상한 | 기간 중 상한이 변경되면 “중단”한다고만 되어 있고 기존 초안 급여 삭제·재계산·상태 복구 절차가 없습니다. 계약 기간별 상한 검증, 계산 실패 시 원자적 롤백, 관리자 조치 절차를 정의해야 합니다. |
| F-015 | 근태 수정과 급여 확정의 날짜 범위 검증 부족 | P0 | FAIL | 제5장 5.4, 제6장 6.3 | 근태의 `work_date` 하나만 검사하면 수정된 출퇴근 시각이 다른 날짜·다른 정산 기간으로 이동하는 경우를 놓칠 수 있습니다. 수정 전·후 양쪽 날짜와 양쪽 급여 기간을 모두 계산해 확정 상태를 검증해야 하며, MVP에서 날짜 이동을 금지한다면 DTO와 서비스에서 명시적으로 거절해야 합니다. |
| F-016 | 스키마 상태값 제약 부족 | P1 | WARN | `member.role`, `employment_status`, `clock_in_method` DDL | 일부 컬럼은 주석만 있고 `CHECK` 제약이 없습니다. `ROLE_OWNER/ROLE_STAFF`, 재직 상태, 타각 방식, 날짜·상태 조합을 DB 제약 또는 명시적 enum 검증으로 강화해야 합니다. |
| F-017 | 시프트·근태 시간 범위 DB 검증 부족 | P1 | FAIL | `shift_schedule`, `attendance` DDL | 종료 시각이 시작 시각보다 이후인지, 최대 16시간인지, 휴게가 전체 범위 안인지 DDL에 없습니다. 서비스 검증만으로는 수동 SQL·경쟁 요청을 막지 못합니다. 저장 프로시저/트리거 또는 원자적 서비스 검증과 무결성 테스트가 필요합니다. |
| F-018 | 삭제·수정 이력 정책 미정 | P1 | WARN | 전반적인 감사추적 요구사항 | `ON DELETE` 정책이 없고, 원본 근태·계약·시프트 삭제 허용 여부도 정의되지 않았습니다. 감사 대상 테이블은 삭제 금지 또는 논리 삭제로 고정하고, 급여 확정 데이터는 append-only 정책을 명시해야 합니다. |
| F-019 | 인덱스가 업무 조회 패턴을 충분히 반영하지 않음 | P2 | WARN | 제2장 DDL 및 근태·급여 API | `attendance_mod_request(store_id, approval_status, work_date)`, 급여 상태·기간 조회, 계약 유효기간 단일 조회용 복합 인덱스가 명시되지 않았습니다. 실제 쿼리별 실행계획 검증과 인덱스 기준을 추가해야 합니다. |
| F-020 | 시간대·현재일 기준 실행 계약 부족 | P1 | WARN | 제1장 `Asia/Tokyo` 원칙; 각 서비스의 `LocalDate.now()` | 애플리케이션 JVM, DB 세션, 커넥션 풀 시간대가 일치하는 설정과 테스트가 없습니다. `Clock` 주입, `ZoneId.of("Asia/Tokyo")` 사용, 자정 전후 통합 테스트를 명시해야 합니다. |
| F-021 | 스키마 초기화·마이그레이션 전략 미완성 | P1 | FAIL | 제1장과 제2장 `CREATE TABLE IF NOT EXISTS` 주의사항 | 기존 테이블을 변경하지 못하는 DDL인데 버전 관리되는 migration 도구나 실행 순서가 없습니다. Flyway/Liquibase 또는 명시적 개발 DB 재생성 절차를 선택하고, 운영 데이터에 대한 초기화 금지 정책을 실행 가능한 형태로 작성해야 합니다. |
| F-022 | 보안 경계가 요구사항 수준에 머묾 | P0 | FAIL | 제1장 1.2.1, 1.3 | 메뉴 숨김이 보안 경계가 아니라고 명시했지만 API별 OWNER/STAFF/소속 검증 행렬, CSRF 정책, 세션 고정 방지, IDOR 테스트가 없습니다. 엔드포인트별 권한·소유권 검증 표와 통합 보안 테스트를 추가해야 합니다. |
| F-023 | 급여 확정 API 재검증 계약 불완전 | P0 | FAIL | 제6장 `expectedGrossPay`, `expectedTotalPay` | 두 요청 필드가 사실상 같은 의미이며 `changedDiff`의 구조도 정의되지 않았습니다. 단일 `expectedGrossPay`로 통일하거나 총액·구성요소별 기대값을 구분하고, 불일치 응답 schema와 재확인 절차를 명시해야 합니다. |
| F-024 | 감사 증적 요구사항 부재 | P1 | WARN | 전체 DoD와 승인 이력 요구 | 누가 언제 어떤 요청·SQL·계산 버전을 사용했는지 보존하는 실행 증적 schema가 없습니다. 승인·확정·재계산 이벤트에 actor, timestamp, before/after hash, rule version을 기록해야 합니다. |

## 우선 수정 순서

1. **P0 차단 항목**: F-001, F-002, F-003, F-004, F-005, F-007, F-015, F-022, F-023  
2. **급여 계산·상태 규칙 통일**: F-012, F-013, F-014  
3. **DTO·오류·시간대 계약 확정**: F-008, F-009, F-010, F-020  
4. **DB migration·인덱스·감사 증적 보강**: F-016, F-018, F-019, F-021, F-024  

현재 문서의 DoD만으로는 “확정 급여의 일반 재계산 변경 0건”과 “동시성 경쟁 시 장부 오염 0건”을 입증할 수 없습니다. 위 P0 항목을 문서·DDL·서비스·통합 테스트에 반영한 뒤 재감사해야 최종 PASS 판정이 가능합니다.
